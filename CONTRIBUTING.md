# Участие в разработке

Спасибо, что хотите помочь. Здесь — как собрать CMS из исходников, проверить изменения и выпустить
релиз. Как устроен код и почему так — в [docs/](docs/README.md).

## Что нужно

- [Bun](https://bun.sh) 1.4.4 или новее — рантайм, менеджер пакетов, тесты и сборка.
- git. Больше ничего: база — SQLite внутри Bun, менеджер собирает Vite из `node_modules`.

## Первый запуск

```sh
git clone https://github.com/a-sharapov/eile.git
cd eile
bun install          # заодно ставит зависимости менеджера (manager/)
bun run dev          # сайт на http://localhost:8080, база site.db, перезапуск при изменениях
```

На пустой базе создаются страница приветствия и пустой шаблон. Сайт с содержимым —
`bun src/main.ts new blog --db site.db`. Пока пользователей нет, сервер печатает ссылку, по которой
создаётся администратор.

Менеджер с горячей перезагрузкой — во втором терминале:

```sh
bun run dev:manager                                   # Vite; API идёт к серверу на :8080
CMS_API=http://localhost:8090 bun run dev:manager     # если сервер на другом порту
```

Откройте адрес, который напечатает Vite, и путь `/manager`.

## Команды

| Команда                   | Что делает                                                            |
| ------------------------- | --------------------------------------------------------------------- |
| `bun run dev`             | Сервер с перезапуском при изменениях                                  |
| `bun run dev:manager`     | Менеджер на Vite с горячей перезагрузкой                              |
| `bun run start`           | Сервер без перезапуска                                                |
| `bun run check`           | Всё перед коммитом: Biome, типы, проверка менеджера, тесты            |
| `bun run test`            | Тесты: домен, интеграция, правила архитектуры (`NODE_ENV=production`) |
| `bun run typecheck`       | Проверка типов                                                        |
| `bun run lint`            | Biome: формат и линт                                                  |
| `bun run format`          | Форматирование Biome                                                  |
| `bun run build:manager`   | Сборка менеджера в `manager/build`                                    |
| `bun run build`           | Один бинарник `dist/cms` под эту машину                               |
| `bun run release build …` | Бинарники под платформы релиза в `dist/release` (см. «Релиз»)         |
| `bun run site`            | Промо-сайт Eile в `eile.db` (см. «Промо-сайт»)                        |

Параметры сервера: `--port` (или `PORT`), `--db` (или `CMS_DB`), `--trust-proxy` (или
`CMS_TRUST_PROXY=1`), `--host` (или `CMS_HOST`), `--media-cache` (или `CMS_MEDIA_CACHE`). Медиатека отдаётся из кэша на диске
`site.media-cache` рядом с базой ([ADR 0038](docs/adr/0038-media-cache.md)); `bun run dev` кладёт его рядом с
`site.db`, удалять его можно когда угодно. Тесты на базе в памяти работают без кэша, прямо из базы; кэш на диске
проверяет `tests/media-cache.test.ts`.

## Где что

| Путь                      | Что там                                                                        |
| ------------------------- | ------------------------------------------------------------------------------ |
| `src/app.ts`              | Корень композиции: собирает контексты в приложение                             |
| `src/main.ts`, `src/cli/` | CLI и `Bun.serve`                                                              |
| `src/contexts/<имя>/`     | Ограниченные контексты: `domain`, `application`, `infrastructure`, `interface` |
| `src/kit/`                | Набор готовых компонентов для «Элементов»                                      |
| `src/scaffolds/`          | Каркасы сайтов для `cms new` и приветствие новой базы                          |
| `manager/`                | Менеджер: SvelteKit 3, свой `package.json`                                     |
| `tests/`                  | Интеграционные тесты и правила архитектуры; доменные тесты лежат рядом с кодом |
| `scripts/`                | Сборка бинарника и релиза                                                      |
| `site/`                   | Промо-сайт Eile, сделанный на самой Eile; в бинарник не входит                 |
| `install.sh`              | Установщик `curl … \| bash`                                                    |
| `docs/`                   | Видение, суть Evo, глоссарий, архитектура, ADR, дорожная карта                 |

## Как писать код

- **Стиль** — [docs/code-style.md](docs/code-style.md): `pipe` и `reduce`, без early return, таблица вместо
  цепочки `if`, `.then` вместо `async`/`await`, `export var`, фабрики `define*`, агрегаты как данные,
  ошибки через `fail()`.
- **Слои и контексты** — [docs/architecture.md](docs/architecture.md). Правила зависимостей проверяет
  `tests/architecture.test.ts`: если он мешает, расширьте публичный API контекста, а не обходите правило.
- **Термины** — из [docs/glossary.md](docs/glossary.md). Новый термин сначала появляется в глоссарии.
- **Язык.** Идентификаторы — на английском, комментарии (только необходимые) и документация — на русском.
- **Решения.** Неочевидный выбор — ADR в [docs/adr/](docs/adr/) с контекстом, решением и последствиями.
- **Evo — справочник поведения, а не код.** Исходники Evo не переводим построчно: описываем, что
  делает Evo, и реализуем своё ([ADR 0004](docs/adr/0004-clean-room-from-evo.md)).
- **Менеджер** — Svelte 5 на рунах и SvelteKit 3; цвета, отступы и состояния — из
  `manager/src/lib/theme.css` и [DESIGN.md](DESIGN.md).

## Промо-сайт

Сайт самой Eile — обычный сайт на Eile: шаблоны и компоненты в `site/*.svelte`, страницы RU и EN, подписи
компонентов (переводы) и свои настройки — в `site/index.ts`, шрифты — в `site/assets/fonts` (OFL),
скриншоты менеджера берутся из `docs/assets`. В `cms new` и бинарник он не входит.

```sh
bun run site --db eile.db --url https://example.com   # собрать базу; --force — пересобрать заново
dist/cms --db eile.db                                  # и отдать её как любой сайт
```

После сборки сайт правится в менеджере, как любой другой: тексты разделов — в страницах `Eile` и `en`,
подписи — в «Настройки → Переводы». `tests/promo-site.test.ts` проверяет, что каждый блок рисуется и у
каждого ключа есть текст на обоих языках.

Кукбук (`/cookbook`, по-английски `/en/cookbook`) — учебник для новичков: сайт кухонной студии от установки
до HTTPS. Главы лежат в `site/cookbook/ru/` и `site/cookbook/en/` и идут парами: переключатель языка ищет
главу-пару по месту, поэтому порядок и число глав в двух языках одни. HTML глав собирают помощники из
`site/cookbook/markup.ts`; шаблоны `Cookbook` и
`Chapter` подсвечивают код на сервере. Пример с пометкой `save` — это элемент, который читатель
сохраняет в менеджере. `tests/promo-cookbook.test.ts` проходит главы каждого языка по порядку на пустой базе
(английские — на английском приветствии), как читатель (`site/cookbook/replay.ts`), и после каждой проверяет страницы студии: изменили пример — тест
скажет, если он сломался. Снимки глав — в `site/assets/cookbook/`: экраны менеджера в двух темах,
страницы студии в светлой (как их видит посетитель, без панели правки); английские снимки — с приставкой
`en-`, их снимает английский менеджер.

На главной поверх большого скриншота стоит кнопка ролика: остров `DemoVideo` играет
`site/assets/video/howto-ru.mp4` (на английской главной — `howto-en.mp4`) на месте снимка, без JS кнопка открывает файл. Ролик — запись настоящей сессии Eile по первым главам кукбука,
музыка сгенерирована локально (ACE-Step, MIT), звуки интерфейса — Kenney (CC0); откуда что, записано рядом в
`.json`. Ролика на языке нет — нет и кнопки: файл ищется как `video/howto-<язык>.mp4`.

## Перед pull request

1. `bun run check` — зелёный. Новая логика покрыта тестом: доменный — рядом с кодом, интеграционный — в
   `tests/` через `createApp()`. Названия тестов — по-русски.
2. Если менялись рантайм, сборка или CLI — `bun run build` и запуск `dist/cms --db <временная база>` из
   каталога вне репозитория: бинарник не должен зависеть от `node_modules`.
3. Если менялся интерфейс менеджера — посмотрите его в светлой и тёмной теме.
4. Сообщение коммита — по-английски, одной строкой о сути и абзацем о том, зачем
   (`Forms can be deleted from the list, with the pages they stand on`).

CI (`.github/workflows/ci.yml`) повторяет проверку на каждый push в `main` и на каждый pull request.

## Релиз

Версия записана в двух местах — `package.json` и `src/cli/version.ts`; их совпадение проверяет
`tests/cli.test.ts`.

```sh
# поднять версию в обоих файлах, закоммитить, затем:
git tag v0.2.0
git push origin v0.2.0
```

Тег запускает `.github/workflows/release.yml`:

1. проверка: тег совпадает с версией, `bun run check`, shellcheck установщика;
2. бинарники под Linux — x64 и arm64, glibc и musl; пробный запуск на Ubuntu и в Alpine;
3. бинарники под macOS — Intel и Apple Silicon, подпись ad-hoc с правами на JIT
   (`scripts/entitlements.plist`) и пробный запуск;
4. сжатые копии `cms-<система>-<процессор>.gz`, `SHA256SUMS` и `install.sh` с адресом этого репозитория;
   установщик ставит собранное из `file://` и запускает;
5. GitHub Release с заметками из коммитов. Тег с дефисом (`v0.2.0-rc.1`) — пре-релиз, если стабильный
   релиз уже есть: `latest` на пре-релизы не указывает. Пока стабильных нет, альфы и беты публикуются
   обычными релизами — иначе установка одной строкой вела бы в пустоту.

Перезапустить публикацию для существующего тега — «Run workflow» у Release с этим тегом.

Собрать релиз локально:

```sh
bun run release build linux-x64          # без целей — все: linux-{x64,arm64}[-musl], darwin-{x64,arm64}
bun run release pack --repo owner/name   # .gz, SHA256SUMS, install.sh
CMS_DOWNLOAD_URL="file://$PWD/dist/release" CMS_INSTALL_DIR=/tmp/cms-bin bash dist/release/install.sh
```

`cms update` и его откат проверяются без особой сборки: своя лента релизов в формате GitHub на этой машине
(`/repos/<owner>/<name>/releases` со ссылками на файлы из `dist/release`) и `CMS_RELEASES_URL=http://127.0.0.1:<порт>`
перед `cms update`. Для отката в ленту кладётся выпуск с номером новее, чей «бинарник» на `version` отвечает, а
сайт не поднимает (скрипт `#!/bin/sh` с `echo "Eile 9.9.9"`): пробный запуск он пройдёт, а 200 на `/_cms/health`
служба на нём не даст ([ADR 0048](docs/adr/0048-health-releases-url-redirect-check.md)).

Бинарники для macOS, собранные на Linux, перед запуском на Mac нужно подписать (`codesign --sign -`);
в CI их собирает и подписывает раннер macOS.

## HTTPS на стенде

Как включить HTTPS на сервере — в README. Для проверки без настоящего домена: `CMS_ACME_DIRECTORY=<адрес
