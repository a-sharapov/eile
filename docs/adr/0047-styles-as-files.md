# 0047. Стили шаблонов и компонентов — файлами с хэшем: общий файл сайта и свои файлы для правил на весь документ

- Статус: принято
- Дата: 2026-11-03

## Контекст

Svelte печатал CSS каждого нарисованного компонента в `<head>` страницы (`css: "injected"`, ADR 0003). Страницы
отдаются с `Cache-Control: no-cache`, поэтому один и тот же CSS уходит с каждой страницей и с каждым просмотром.
Замер на копии живого сайта, главная:

- HTML — 158 562 байта, brotli — 32 938;
- из них 105 808 — CSS компонентов в 13 блоках `<style id="svelte-…">`;
- планер и страница для студий несут ещё 48 и 78 КБ того же CSS: Layout, шапку, подвал, окно cookie.

Скрипты сайта уже отдаются файлами с хэшем и `immutable` (ADR 0039). Стилям нужно то же, но с двумя условиями.
Вид не должен измениться ни на пиксель. Мигания без стилей быть не должно.

## Решение

**CSS рендера забирается, а не печатается.** Каждый скомпилированный вид кладёт свой `$$css` (`{ hash, code }`) в
набор рендера, а Svelte печатает набор в head, когда корень нарисован. `svelteViewRenderer` рендерит корень-
обёртку. Она вызывает вид, забирает набор по порядку рендера и очищает его до печати. Набора нет, например в
другой версии Svelte, — стили остаются в head, как раньше. Компиляция не меняется: тот же `css: "injected"`,
поэтому классы области в HTML и в файлах одни и те же.

**Каталог стилей** (`design/infrastructure/site-styles.ts`) знает CSS каждого шаблона и компонента сайта. Он
берёт его из той же компиляции, что и загрузчик видов: `defineServerCompiler` держит последнюю компиляцию
каждого элемента по исходнику, и её делят проверка при сохранении, виды и стили. Константу `$$css`
`liftStyle` находит по синтаксическому дереву модуля (acorn), а не по тексту.

**Раскладка: общий файл сайта плюс свои файлы.**

- **Общий файл** `/_cms/styles/site.<хэш>.css` собирает CSS, который привязан к своему компоненту. Такой CSS
  действует только там, где компонент нарисован, поэтому его можно держать на каждой странице. Это CSS, где
  в каждом селекторе есть класс области (`.card.svelte-1abc`, `.a.svelte-1abc :global(.prose)`), вложенные
  правила привязаны через родителя, а анимации названы с префиксом области. Проверяет `isScoped`: он разбирает
  CSS через `parseCss` из `svelte/compiler`, а не самодельным разбором. Внутри `@media`, `@supports`,
  `@container`, `@layer`, `@scope` и `@starting-style` проверяются правила.
- **Свой файл** `/_cms/styles/<Имя>.<хэш>.css` получает элемент, у которого есть правило на весь документ:
  `:global(body)`, `:global(:root)`, `@font-face`, `@property`, `@import`, `@layer a, b;`, `-global-`
  анимация. Такой файл подключают только страницы, где элемент действительно нарисован. Это решает рендер, а
  не граф импортов: компонент за ложным `{#if}` свой файл не подключит. Глобальные правила одного шаблона
  поэтому не протекают на страницы другого. `@import` в начале стиля остаётся в начале файла и работает,
  как работал в `<style>`.
- **В странице остаётся** стиль элемента с `<svelte:options css="injected" />`: автор просит именно этого.
  В странице остаётся и стиль, которого нет в каталоге, например вид старше каталога. Оба выводятся так, как
  выводил Svelte. Остров с таким стилем при гидрации не вставит его второй раз: Svelte в браузере находит
  `<style id>` и ничего не добавляет.

**Порядок, как печатал Svelte, насколько это возможно.**

- Теги стоят в конце head вида, до SEO-шапки и head регионов. Разметка `<svelte:head>` (шрифты, сторонние
  стили) идёт раньше них, а стили форм `:where(.cms-form …)` (ADR 0021), как и прежде, после.
- Свои файлы и `<style>` идут в порядке рендера, общий файл — последним. Общий файл совпадает с элементами
  только своими правилами, и ничья по специфичности возможна лишь с глобальными правилами. Их обычно пишет
  рамка сайта, родитель, и Svelte печатал её раньше детей. Внутри общего файла родитель тоже раньше детей:
  шаблоны по имени, за каждым его импорты, затем остальные компоненты.
- Регион рисуется во второй фазе. Его стили дописываются после head регионов, только те, которых ещё нет.

**Хэш и кэш.**

- Хэш — `Bun.hash` содержимого файла. Правка разметки без правки стиля его не меняет, и файл остаётся в кэше
  браузера.
- Правка любого шаблона или компонента сбрасывает тег `styles`. Его пишет первая фаза каждой страницы со
  стилями (`STYLES_TAG`, `delivery/index.ts`), и страницы перерисовываются с новыми адресами, как у
  `script(name)`. Каталог собирается заново на первом запросе после события `design.*`. Компилируются только
  изменённые элементы.
- `cms elements push` и `cms mcp` пишут в базу другим процессом. Сервер видит новый `data_version`, собирает
  контексты заново, и каталог считается с нуля. Перезапуск не нужен (проверено на копии живого сайта и в
  `tests/shared-database.test.ts`).
- Отдаёт `design/interface/file-handler.ts`, общий со скриптами сайта. Ответ — `text/css; charset=utf-8`,
  `nosniff`, `public, max-age=31536000, immutable`, ETag (у сжатой копии свой), 304, HEAD, br или gzip;
  другие методы — 405.
- **Прежний хэш — текущая версия с `Cache-Control: no-cache`, а не 404.** У скриптов прежний хэш — 404
  (ADR 0039). Страница без стилей хуже, чем страница без сцены: HTML, полученный за миг до правки, иначе
  нарисовался бы голым. Классы области зависят от имени файла, а не от версии, поэтому новый CSS подходит и к
  прежнему HTML. Незнакомое имя и кривой путь — 404.

**Что не меняется.** Markdown-версия собирается из HTML страницы, но head в неё не входит. Карта сайта и
`llms.txt` из HTML-документа не строятся. У страниц-файлов (CSS, лента, SVG) head нет, ссылок на стили они не
получают. Полоса правки (ADR 0032) вставляется перед `</body>` и живёт в теневом DOM со своими стилями.
Редактор в окне — сам менеджер. Предпросмотр из менеджера работает в песочнице CSP: файлы стилей грузятся как
обычные внешние стили. Острова компилируются для браузера с `css: "external"` (ADR 0008) и стилей не
вставляют: их CSS уже в файлах страницы.

## Замеры (копия живого сайта, 17 опубликованных страниц, brotli 9 как у сервера)

| Раскладка                            | Что скачивается                                                                   | Визит главная → планер → студиям, CSS                    |
| ------------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------- |
| В странице (было)                    | главная 103,8 / 21,0 КБ, планер 46,5 / 10,3, студиям 72,9 / 14,7                  | 46,0 КБ, и снова на каждой странице                      |
| По набору компонентов страницы       | 12 разных наборов на 17 страниц; у трёх страниц визита наборы разные              | 46,0 КБ, плюс три запроса                                |
| По шаблону                           | Landing (10 страниц) — 156,0 / 28,7 КБ, второй шаблон (3) — 33,9 / 8,3            | 28,7 КБ; переход на второй шаблон — снова Layout         |
| Один файл на сайт                    | 157,5 / 29,1 КБ                                                                   | 29,1 КБ, но `:global` всех элементов — на всех страницах |
| **Общий файл и свои файлы (выбран)** | site 100,9 / 17,8 КБ; Layout 18,3 / 5,2; KitchenStage 38,4 / 9,2 (только главная) | **32,2 КБ один раз**                                     |

Первое число — несжатый CSS, второе — brotli. Набор компонентов страниц почти весь сайт: объединение блоков
всех страниц — 156,3 КБ из 157,5. Поэтому раскладки по набору и по шаблону кэшу почти ничего не дают.
Свои файлы обходятся в 3 КБ brotli против одного файла на сайт: малые файлы сжимаются хуже. За эти 3 КБ стили
каждой страницы остаются ровно такими, как раньше.

Визит из трёх страниц с кэшем браузера, байты по проводу (brotli; gzip — в скобках):

| Страница   | Было: HTML      | Стало: HTML     | Стало: CSS                                |
| ---------- | --------------- | --------------- | ----------------------------------------- |
| Главная    | 32 938 (36 181) | 12 320 (13 313) | 32 230 (34 294), 3 файла                  |
| Планер     | 17 503 (18 616) | 7 360 (7 868)   | 0 — уже в кэше                            |
| Для студий | 26 368 (28 894) | 12 009 (12 888) | 0 — уже в кэше                            |
| Всего      | 76 809 (83 691) | 31 689 (34 069) | 32 230 (34 294); с HTML — 63 919 (68 363) |

Несжатый HTML главной — 54 079 байт вместо 158 562. Каждая следующая страница визита и повторный визит, когда
файлы стилей уже в кэше, весят на 54–63 % меньше. Первая страница после запуска сервера рисуется за 0,40 с
вместо 0,25: каталог компилирует все элементы. Следующая незакэшированная страница — 8 мс вместо 34, всё уже
скомпилировано.

**Проверка вида.** Серверы `main` и ветки работали на двух копиях базы живого сайта. Снимали 17 опубликованных
страниц и 404 в 1440×900 и 390×844, headless Chrome по CDP. Шрифты дождались, анимации заморожены, canvas и
video скрыты в обоих прогонах. Все 36 снимков совпали байт в байт. Вычисленные стили 20 862 элементов
(и `::before`/`::after`), в том числе с `:hover` и `:focus-visible` на всех ссылках и кнопках, совпали.
Исключение — три элемента главной, которые анимирует скрипт сцены: они расходятся и между двумя прогонами
`main`. Сравнение стилей нашло и единственное расхождение первой версии: ссылки стояли после head регионов, и
стили форм уступали `:where(input…)` Layout. Отсюда правило «до SEO-шапки и регионов». Полоса правки, окно
редактора и предпросмотр совпали снимками.

## Последствия

- Любая правка шаблона или компонента перерисовывает все страницы со стилями при следующем запросе, а не
  только страницы с этим элементом. Даже правка одной разметки, у которой хэш общего файла не меняется. Правка
  Layout и раньше сбрасывала всё. Рендер — миллисекунды, а файлы в кэше браузера при неизменном CSS остаются.
- Глобальное правило в компоненте стоит своего файла и запроса на страницах, где компонент нарисован. Правила
  на весь документ лучше держать в рамке сайта (`Layout`), а у остальных компонентов — привязывать к своему
  элементу: `.card :global(a)`, `html:has(.kx) …`.
- Первая страница после запуска и после `cms elements push` ждёт компиляции всех шаблонов и компонентов: на
  живом сайте это 41 элемент и около 0,15 с.
- Порядок CSS — тот же внутри элемента, но не между элементами: общий файл идёт после своих файлов. Ничья по
  специфичности между глобальным правилом одного элемента и привязанным правилом другого теперь решается этим
  порядком. На живом сайте таких ничьих нет (проверено сравнением вычисленных стилей).
- Захват набора опирается на `$$renderer.global.css` — тот вызов, что Svelte вставляет в каждый
  скомпилированный компонент. Если его не станет, стили останутся в странице, а тест
  `tests/styles.test.ts` («в странице нет `<style>`») это покажет.

## Отклонённые варианты

- **Один файл на весь сайт.** Самый простой, на 3 КБ меньше. Но `:global(body)` одного шаблона красил бы
  страницы другого, а правило компонента, нарисованного только на главной, действовало бы везде.
- **По шаблону или по набору компонентов страницы.** На живом сайте наборы почти совпадают с сайтом целиком, а
  компоненты текста страниц к шаблону не привязаны. Кэш между страницами визита они почти не дают.
- **`css: "external"` и CSS из `compile().css`.** Svelte сжимает CSS только при `injected`, во внешнем CSS
  остаются пробелы и комментарии `/* (unused) */`: +20 % несжатого CSS, +4 % brotli. И признак `hasGlobal`
  есть только там. Компиляция дважды удвоила бы время. Своя проверка по `parseCss` строже и обходится одной
  компиляцией.
- **Прежний хэш — 404, как у скриптов.** Страница, открытая за миг до правки, осталась бы без стилей.
