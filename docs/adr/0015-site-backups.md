# 0015. Копии сайта: файл базы и записи в JSON

- Статус: принято
- Дата: 2026-10-30

## Контекст

Сайт целиком — один файл SQLite: страницы, элементы, медиатека (BLOB), настройки, пользователи. Копию
снимала команда `cms backup`, восстанавливали подменой файла при остановленном сервере. Владельцу
сайта нужно то же в менеджере, а ещё — копия, которую можно прочитать, сравнить и перенести.

## Решение

- **Два вида копии.** `.db` — снимок `VACUUM INTO`, точный и быстрый. JSON — те же записи текстом:
  `{ format: "cms-archive", version: 1, migrations, tables }`, BLOB — `{ "$base64": … }`.
  Модуль `platform/archive.ts` работает с таблицами и о контекстах не знает.
- **Один путь восстановления.** JSON собирается во временную базу: миграции, которые были у копии, её
  записи, затем недостающие миграции. Файл `.db` проверяется (есть журнал `_migrations`, нет чужих
  миграций) и тоже доводится до текущей схемы. Записи переносятся в рабочую базу одной транзакцией:
  каждая таблица очищается и заполняется из копии по общим столбцам.
- **Копия из более новой версии** не принимается (`backup.newer`): её схему эта программа не знает.
- **Копия — чужой файл.** Загруженная база проверяется `PRAGMA quick_check` и открывается с
  `trusted_schema = OFF`; из неё берутся только настоящие таблицы, имена таблиц из JSON — только известные
  схеме. Восстановление чужой копии приносит её пользователей и её код — менеджер предупреждает об этом.
- **Сеансы входа и подключение ИИ не копируются** ни в JSON, ни в `.db` (из снимка они вычищаются, файл
  пересобирается, чтобы строки не остались в свободных страницах), а при восстановлении остаются свои:
  старые токены из копии ожили бы снова, ключ ИИ ушёл бы с сервера. Файл копии — с правами 600,
  временные копии — в своём каталоге (700), а не в общем `/tmp`. Сеанс закрывается, если под тем же id в копии другая почта — иначе вошедший стал бы чужой
  учётной записью.
- **Кэши не переживают замену записей.** Корень композиции собирает контексты заново на той же базе
  (`_compose`): страницы, скомпилированные шаблоны и плагины берутся уже из копии. `App` отдаёт
  контексты через геттеры, поэтому ссылки на него остаются верными.
- **Прежнее состояние** сохраняется рядом с файлом базы (`site.before-restore-ГГГГММДД-ЧЧММССммм.db`),
  если в базе было что терять; хранятся три последних. Это полный снимок сервера — с сеансами и ключом
  ИИ, поэтому только владельцу (600). Восстановление — только администратору (`site.edit`).

## Следствия

- Менеджер: раздел «Копии» в шапке (администратору) — скачать `.db` или JSON, восстановить из любого
  вида, строка cron для копий по расписанию.
  CLI: `cms backup site.json` и `cms restore <файл>`; восстановление в новую базу — переезд
  на другой сервер.
- JSON с медиатекой большой (base64 на треть больше файлов); тело запроса сервера — до 2 ГиБ.
- Новая миграция не ломает старые копии: они доводятся до схемы при восстановлении.
