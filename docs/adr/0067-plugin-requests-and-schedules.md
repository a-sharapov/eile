# 0067. Плагин отвечает на запрос и работает по расписанию

- Статус: принято
- Дата: 2026-11-08

## Контекст

На сайте Evo gabriel.by часть работы жила в плагинах на `OnPageNotFound`, которые отвечали сами и делали
`exit`:

- `GET /api/v1/landing?type=detail&item=<slug>` — JSON изделия для отдельного лендинга granitmemorial.by,
  `type=examples&item=<key>` — JSON-список;
- `POST /api/v1/landing?token=…&type=process` — заявка JSON-ом с granitmemorial.by и со статического сайта
  `/razbor/`, дальше письмом;
- `GET /api/v1/landing/payment?payload=a::key` — `{ result, signature: sha1(payload + secret) }` для WebPay;
- `GET /api/v1/health` — `{"status":"alive"}`, `GET /api/v1/cy` — `{"course":"<курс USD>"}`.

Все отвечают с `Access-Control-Allow-Origin: *` и на `OPTIONS`. У них внешние потребители: их адреса и ответы
должны пережить переезд. Ещё одна часть — задание priceParser: раз в 12 часов курс USD→BYN с floatrates.com в
системную настройку, от которой считается каждая цена на сайте.

Плагин Eile умел три вещи: `render` (последнее слово о HTML), `notFound` (адрес редиректа вместо 404) и `on`
(события). Ответить на запрос сам, принять POST или проснуться по таймеру он не мог.

## Решение

```ts
export default {
  render?(html, { path, status }): string,
  notFound?(path): string | null,
  handle?(request: Request, context): Response | null | Promise<Response | null>,
  schedule?: { every: '12h' | '15m' | number, run(context): void | Promise<void> },
  on?: { [событие]: (event) => void },
};
```

### `handle` — свой ответ на запрос

**Когда спрашивают.** Когда на запрос не ответило ничто на сайте. Порядок ответа целиком:

1. проверка здоровья `/_cms/health`, менеджер, `/_cms/…`, формы, поиск, предпросмотр, `/media/…`, почтовый шлюз;
2. файл связанной папки по исходному адресу и адреса папки-сайта ([ADR 0065](0065-linked-folders.md),
   [ADR 0068](0068-static-site-folder.md));
3. Markdown, `robots.txt`, `sitemap.xml`, `llms.txt`; правило с query; страница (с кэшем страниц);
4. правило переадресации, прежний адрес страницы, `/old/` → `/old` у сайта без адресов на `/`;
5. **`handle` плагинов**, затем `notFound` плагинов;
6. страница 404 сайта.

- **Любой метод.** GET и HEAD доходят до `handle` после шагов 3–4. Другие методы (POST, PUT, DELETE, OPTIONS…)
  страницы, правила и прежние адреса не обслуживали и отвечали 405; теперь такой запрос сразу спрашивает
  плагины, и только без их ответа — 405, как раньше. Так плагин принимает POST и preflight `OPTIONS` и на
  адресе, где есть страница: на GET там по-прежнему страница.
- **Порядок плагинов — по имени**, как у остальных хуков (`ORDER BY name`); первый, кто вернул `Response`,
  выигрывает. `null` или `undefined` — дальше. Вернул не `Response` — сбой плагина в журнал и дальше.
- **`handle` раньше `notFound`.** Плагин, который отвечает на свой адрес, точнее, чем плагин, который ведёт
  всё неизвестное на главную: иначе такой «редирект всего» закрыл бы API. Плагин только с `notFound` работает,
  как раньше.
- **Срок — 5 секунд.** Bun закрывает соединение после 10 секунд тишины; за 5 посетитель ещё получает страницу
  404. Срок вышел — сбой плагина в журнал и в каналы сбоев (`extensions.plugin_failed`), запрос идёт дальше,
  `context.signal` прерывается: `fetch(url, { signal: context.signal })` в плагине оборвётся сам. Работа
  плагина, который `signal` не слушает, продолжается в фоне — отменить чужой промис нельзя.
- **Исключение** (синхронное или отказ промиса) — так же: журнал, сбой, дальше другие плагины и 404 (у GET)
  или 405.
- **Кэш страниц ответа плагина не видит.** Ответ уходит как есть: без `x-cache`, ETag, сжатия, полосы правки,
  счётчика просмотров и хука `render`. Кэшировать — заголовками самого ответа. У HEAD тело ответа
  отбрасывается.
- **Каждый плагин получает свою копию запроса** (`request.clone()`): тело, прочитанное одним, прочитает и
  следующий.
- **Тело — не больше 64 КБ**, как у формы без файлов ([ADR 0021](0021-forms.md)), тем же `readBody` из
  `platform/body.ts` ([ADR 0043](0043-large-bodies-memory.md)): по Content-Length сразу, chunked — по ходу. Больше
  — 413 до плагина, оборванное посетителем — 400. Bun.serve пропускает до 2 ГиБ ради восстановления копии;
  до плагина они не доходят. Тело читается, только если среди включённых есть плагин с `handle`: без таких
  ответ прежний, 405.

### Контекст плагина

Второй аргумент `handle` и аргумент `schedule.run`:

| Что                              | Зачем                                                                                                       |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `site()`                         | Настройки сайта и свои настройки `custom` — снимок на момент вызова; нет ключа — `undefined`, а не `[@key]` |
| `setCustom(key, value)`          | Своя настройка сайта через контекст `site`: те же проверки ключа и длины, что в менеджере, событие, кэш     |
| `submit(form, values, options?)` | Заявка существующей формы от кода сервера; `{ ok: true, id, spam }` или `{ ok: false, errors }`             |
| `log(...parts)`                  | Строка в вывод сервера с именем плагина в начале                                                            |
| `signal`                         | Прерывается, когда срок вызова вышел                                                                        |

- **Данные страниц — по-прежнему из `$core`** (`page`, `children`, `listing`, `link`, `media`, `setting`):
  плагин импортирует только его. `context.site()` повторяет `site()` из `$core` намеренно и с отличием: в коде
  сервера отсутствующий ключ лучше `undefined`, чем строка `[@usdRate]`, — `Number('[@usdRate]')` дал бы `NaN` в
  ценах. Остальное в контексте — то, чего в `$core` нет: запись и срок.
- **`setCustom`** пишет через `site.customSettings.set`: пояснение настройки из менеджера остаётся, событие
  `site.custom_settings_changed` сбрасывает кэш страниц (все страницы: `[@key]` и `site.custom` может читать
  любая). То же значение — ни записи, ни события: задание раз в 12 часов не сбрасывает кэш зря. Ответ —
  изменилось ли. Неверный ключ — исключение `site.invalid_key`, как в менеджере.
- **`submit`** — `forms.submitTrusted`: плагин уже принял запрос своим адресом и сам решил, верить ли ему (токен,
  подпись). Поэтому нет печати, ловушки, задачи защиты ([ADR 0053](0053-proof-of-work-forms.md)), минимального
  времени и лимита частоты. Остальное — как у заявки со страницы:
  - в заявку идут только поля из разметки формы и по её правилам (`required`, `type`, `pattern`…);
    неизвестные и служебные `_…` отбрасываются; скрытые поля страницы, сайта и времени заполняет сервер;
  - ошибки полей — `{ ok: false, errors: { поле: текст } }` на языке страницы или сайта, в базу ничего;
  - фильтр спама по содержанию работает: значения обычно прислал посетитель лендинга. Спам записывается со
    статусом «спам», без уведомлений — `{ ok: true, spam: true }`;
  - уведомление в каналы формы, письмо отправителю, вебхук ([ADR 0037](0037-form-webhooks.md)), цель статистики
    и событие `forms.submission_received` — как обычно;
  - `options.page` — id страницы сайта (скрытые поля страницы, адрес заявки); `options.origin` — адрес вне
    сайта, откуда заявка (`https://granitmemorial.by/`): в заявке подписью — хост, адресом — он сам; не
    `http(s)://` — не записывается, туда часто кладут заголовок `Origin` посетителя; `referrer`; `ip` и
    `userAgent` — хранятся по настройке формы `storeClientInfo` и нужны цели статистики;
  - формы нет — исключение `forms.form_not_found`.

### `schedule` — задание по расписанию

- **Период** — `'30s'`, `'15m'`, `'12h'`, `'1d'`, `'1.5h'`, `'2500ms'` или число миллисекунд; от 1 секунды до 24
  дней (дольше `setTimeout` не ждёт). Неверный — сбой `extensions.schedule_failed`, задание не ставится,
  остальное в плагине работает.
- **Только у сервера** (`cms serve`, `createApp({ background: true })`). Команды CLI, `cms mcp` и тесты без фона
  расписаний не запускают.
- **Первый запуск** — через 5 секунд после старта (запуск сервера не ждёт задания), но не позже одного
  периода; дальше — каждый период от начала прежнего запуска.
- **Один запуск за раз** у плагина: тик, пока прежний запуск не кончился, пропускается со строкой в журнале.
  Запуск дольше 10 минут считается зависшим: сбой в журнал и каналы, `signal` прерывается, следующий запуск
  снова возможен.
- **Правка плагина** (исходник, выключение, удаление) снимает его задание; новое ждёт первый запуск заново.
  Таймеры — одни на процесс (`definePluginScheduler`, корень композиции), а не в контексте: после пересборки
  контекстов (восстановление копии, запись другим процессом — `cms elements push`) задание той же версии
  плагина идёт своим ходом с новым контекстом, и два запуска сразу не случатся. `app.close()` снимает все.
  Правку другим процессом сервер, как и всё остальное, видит с первым запросом после неё (`data_version`,
  [ADR 0034](0034-ai-agents.md)): до него идёт прежнее задание.
- **Сбой** — журнал и каналы сбоев (`extensions.schedule_failed`, «Задание по расписанию плагина X не
  выполнилось»), одинаковые склеиваются.

## Проверка

Бинарник `dist/cms` этой ветки вне репозитория, сайт из `cms new blog`, плагин `plugins/Test.ts` через
`cms elements push`: `GET /api/v1/health` — 200 `{"status":"alive"}` с CORS; `OPTIONS` с
`Access-Control-Request-Method` — 204 с CORS; `POST /api/v1/echo` JSON-ом в форму `feedback` через `submit` —
`{"ok":true,"id":1,"spam":false}`, лишнее поле не записано, у заявки `pageTitle: granitmemorial.by`; без
обязательных полей — `{"ok":false,"errors":{…}}`; 70 КБ — 413; `POST /nowhere` — 405, `GET /nowhere` — 404.
Расписание `every: '2s'` с `setCustom('tick', …)` — запуски каждые 2 секунды с первого; правка плагина
(`'3s'`) другим процессом — прежнее задание снято, новое пошло через 3 секунды.

## Почему так

- **Почему не отдельный вид «маршрут плагина» с таблицей адресов.** Плагины Evo так и работали: смотрели на
  адрес и отвечали. Таблица адресов дала бы ещё одно место, где ищут ответ, и всё равно потребовала бы кода.
  Последнее место перед 404 ничего не ломает: страница, правило и файл с тем же адресом важнее.
- **Почему `handle` получает настоящий `Request`.** Плагину нужны метод, query, заголовки и тело — ровно то,
  что даёт веб-стандарт; ответ — `Response` того же стандарта (`Response.json`, CORS заголовками).
- **Почему 5 секунд, а не 10.** На 10-й секунде Bun рвёт соединение сам, и посетитель не получил бы даже 404.
- **Почему контекст, а не новые экспорты `$core`.** `$core` — синхронное чтение для шаблонов и компонентов,
  каждый экспорт — публичный API вида. Запись настройки и заявка из шаблона — дыра, а не возможность.
- **Почему `submit` без лимита частоты.** Лимит считает адрес посетителя, а плагин может его не знать (лендинг
  шлёт с сервера). Решает плагин: токен, подпись, свой счётчик.
- **Почему расписание в плагине, а не cron.** Курс валют — часть сайта: переезжает с ним в копии и правится
  в менеджере. `Bun.cron` с выражением был бы гибче, но период «раз в 12 часов от запуска» — то, что делал
  priceParser, и в нём не ошибиться.

## Последствия

- Плагины Evo на `OnPageNotFound`, которые отвечают сами, переносятся почти построчно: адрес и метод —
  из `request`, ответ — `Response`, данные — из `$core`, заявка — `context.submit`.
- Ответ плагина может перекрыть только то, на что сайт не ответил. Страница с тем же адресом важнее на GET; на
  POST и OPTIONS — плагин.
- `cms help serve` и `cms help elements`, AGENTS.md папки элементов и памятка для моделей описывают новые хуки.
- API: `PluginHooks.{handle,schedule}`, `PluginContext`, `hooks.handle`, `extensions.start`,
  `definePluginScheduler`, `parseEvery`, `forms.submitTrusted`, `site.customSettings.set`, `delivery.notFound`,
  `Delivery.kind = 'response'`, `AppOptions.pluginTimings` (сроки для тестов).
