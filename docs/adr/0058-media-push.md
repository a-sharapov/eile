# 0058. Медиатека из папки: `cms media push`

- Статус: принято
- Дата: 2026-11-05

## Контекст

Код сайта живёт в git, и элементы уже ездят оттуда в базу командой `cms elements push` (ADR 0034). Медиатека — нет.
Сайт, у которого в репозитории лежат шрифты, текстуры, звуки, сотня роликов `.webm` (около 96 МБ) и картинки,
переносил их в базу разработки и в боевую по одному через менеджер. Это долго, легко ошибиться, и после правки
одного ролика непонятно, какие файлы в базе уже устарели.

Нужна та же схема, что у элементов: папка — источник, команда кладёт её в базу, совпавшее не трогает, лишнее
удаляет только по просьбе, а сервер на той же базе видит изменения без перезапуска.

## Решение

```
cms media push [<папка>] [--into <путь>] [--prune] [--dry-run] [--json] [--db <файл>]
```

**Путь в медиатеке — путь файла от корня папки**, через «/»: `fonts/pt-sans.woff2`. С `--into fonts` — под этой
приставкой: `cms media push web/static/fonts --into fonts` даёт `fonts/pt-sans.woff2`. Приставка проверяется по
правилам пути медиатеки, «/» по краям отбрасываются.

**Правила — те же, что у медиатеки, без молчаливых поправок.**

- Путь — `parseMediaPath` и ровно он: `Photo.JPG` медиатека сама превратила бы в `photo.jpg`, и в базе было бы
  другое имя, чем в git. Поэтому другой регистр — ошибка «переименуйте файл», как в пакете каркаса (ADR 0056).
- Тип — `contentTypeOf`, та же таблица: HTML и скрипты в медиатеку не попадают (ADR 0039).
- Размер — `checkSize`: от 1 байта до 25 МиБ (`MAX_MEDIA_SIZE`). Размер берётся из `stat`, файл для этого не
  читается: ролик в 30 МБ отклоняется сразу.
- Символьная ссылка — ошибка, как в папке пакета.
- Скрытое (часть пути начинается с точки: `.git`, `.DS_Store`) и следы архиваторов (`__MACOSX/`, `Thumbs.db`,
  `desktop.ini`) не читаются: правило `isJunk` теперь общее с чтением пакета. Скрытые папки не обходятся вовсе.
- Нарушения собираются по всей папке и печатаются все сразу с путями файлов, как у `cms elements check`. Если
  есть хоть одно, не читается содержимое ни одного файла и не пишется ничего; код выхода 1.

**`media.json` в корне папки — описания картинок**, та же форма, что у `media` в манифесте пакета:

```json
{ "images/hero.jpg": { "alt": "Кухня у окна, утренний свет" } }
```

- Ключи — пути от корня папки, до приставки `--into`: папку можно положить под любой путь, не правя файл.
- Схема строгая: незнакомое поле, не объект, не строка — ошибка `workspace.invalid_media_json`; неверный JSON —
  `workspace.invalid_json`; ключ без файла в папке — `workspace.unknown_media`; описание длиннее 500 знаков —
  `media.invalid_alt`. Описание чистится как в менеджере (`parseAlt`: пробелы схлопываются).
- Файла нет в `media.json` — его описание в медиатеке не трогается: описание, сделанное в менеджере, не пропадёт
  от отправки папки. Пустая строка `"alt": ""` описание стирает — это явная просьба.
- Сам `media.json` в медиатеку не уходит.

**Что изменилось — по хэшу содержимого медиатеки.** Файл с другим размером — изменённый без чтения; с тем же
размером — сверка `mediaHash`, того же хэша, что у ETag, `?v=` и имени в кэше (ADR 0038). Хэш считается окнами по
1 МиБ (`openFile` в `platform/body.ts`): файл в память целиком не поднимается. Совпавший файл не пишется, его `?v=`
и кэши не меняются. Совпавший файл с новым описанием — отдельная строка отчёта (`described`).

**Запись — обычным `media.files.save`, как загрузка из менеджера.** Отсюда всё, что есть у загрузки:

- события `media.file_saved`: кэш страниц сбрасывается по тегу файла, страница получает новый `?v=` и `srcset`;
- кэш медиатеки на диске убирает прежние версии (`--media-cache` команда принимает, как сервер);
- замена оригинала стирает его прежние варианты размеров, новые ставятся в очередь (ADR 0046);
- содержимое передаётся `UploadContent` с окнами по 1 МиБ из файла на диске, а репозиторий пишет куски
  хранения по одному (ADR 0043): ролик в 25 МиБ в памяти CLI целиком не лежит, файлы идут по одному.

**По файлу, а не одной транзакцией.** У `cms elements push` — «всё или ничего» одной транзакцией. Для медиатеки
это хуже: 96 МБ в одной транзакции держат запись в базу секунды, а сервер на той же базе ждёт блокировку не дольше
`busy_timeout` (5 с) — его запись статистики или заявка отвалились бы. Поэтому «всё или ничего» — для проверки:
нарушение правил в папке не даёт записать ни одного файла. Сама запись — по файлу, каждая своей короткой
транзакцией. Если запись оборвалась (диск, сигнал), записанное остаётся, команда говорит «сохранено не всё»,
а повтор пропустит совпавшие файлы и доделает остальное. Удаление с `--prune` идёт только после удачной записи
всех файлов.

**Варианты размеров — сразу.** После записи команда разбирает очередь вариантов (`media.variants.run()`), как
`cms new`: к первому показу страницы `srcset` готов. Сервер на той же базе тоже разбирает очередь раз в минуту;
задание, взятое двумя процессами, не даёт вариантов дважды — запись вариантов проверяет, что их ещё нет (ADR 0046).

**`--prune` — только по просьбе и с защитой.** Без флага ничего не удаляется: файлы медиатеки, которых нет в папке,
перечисляются строкой «нет в папке, в медиатеке остались» (`missing`). С флагом:

- кандидаты — файлы медиатеки без файла в папке; с `--into` — только под этой приставкой, остальная медиатека не
  трогается;
- оригинал удаляется вместе со своими вариантами размеров, как кнопкой «Удалить» в менеджере; варианты оригинала,
  который есть в папке, — его, сервер их сделал, они не удаляются никогда;
- остаётся файл, который стоит на странице (текст, поля, картинка для соцсетей — `content.usage.media`, тот же
  ответ, что менеджер показывает перед удалением), картинка сайта для соцсетей в настройках и файл, чей путь есть
  в исходнике шаблона, компонента или скрипта (`/media/fonts/theme.woff2` в `<link rel="preload">`, `media('…')`).
  Менеджер такой файл удалить даёт, спросив; команда не спрашивает, поэтому оставляет. Поиск пути в исходнике —
  подстрока: лишнее совпадение только оставит файл, а не удалит нужный.
- оставленные файлы печатаются с причиной (`kept`: страницы с id и названием, `site`, элементы файлами папки
  элементов), их варианты остаются с ними.

**`--dry-run`** — та же работа без записи: что добавится, изменится, получит описание и удалится. Хэши
считаются, файлы не пишутся, варианты не режутся.

**`--json`** — отчёт целиком, как у `cms elements push --json`:

```json
{
  "added": ["video/intro.webm"],
  "changed": ["images/hero.jpg"],
  "described": ["images/logo.svg"],
  "removed": [],
  "kept": [
    {
      "path": "images/old.jpg",
      "pages": [{ "id": 12, "title": "О нас" }],
      "site": false,
      "elements": []
    }
  ],
  "missing": [],
  "same": 97,
  "variants": 3,
  "problems": [],
  "saved": true
}
```

Проблема — как у элементов: `{ file, code, message }`, `file` — путь от корня папки. Ошибка — код выхода 1.

**Сервер на той же базе — без перезапуска.** Запись меняет `PRAGMA data_version`, и сервер на следующем запросе
собирает контексты заново (ADR 0034, «Общая база»): кэш страниц пуст, страницы получают новые `?v=` и `srcset`.
Сам файл сервер отдаёт и без этого: обработчик `/media` читает описание из базы на каждом запросе, а файл кэша на
диске назван хэшем — новое содержимое выгружается под новым именем. Это проверяет тест на двух приложениях на
одном файле базы и запуск бинарника ниже.

## Проверка

Бинарник `dist/cms` из этой ветки, вне репозитория, на базе `cms new blog`, Linux x64. Сервер `cms --db site.db`
запущен на той же базе до первой отправки и не перезапускался. Папка — 30 МБ: два шрифта, картинки 2048×2048 и
1600×900 (JPEG), звук, пять роликов по 1,5 МБ, ролик ровно 20 МиБ, `.git/` и `media.json` с двумя описаниями.

- `--dry-run` — 11 файлов к добавлению, ничего не записано. Первая отправка — 11 файлов и 5 вариантов картинок за
  0,78 с.
- Сервер сразу отдал ролик в 20 МиБ (200, `video/webm`, ETag, `content-length` 20971520, побайтно тот же файл) и
  кусок по Range (206). До отправки — 404.
- Повтор — «папка и медиатека совпадают». Другой ролик того же размера — один изменённый файл, сервер отдаёт новое
  содержимое с новым ETag. Страница с `[[Figure src="images/hero.jpg"]]` после замены картинки получила новые `?v=`
  у оригинала и вариантов 480 и 960 и описание из `media.json` — без перезапуска сервера.
- Файл в 27 МБ — `media.invalid_size`, код выхода 1, ничего не записано. `--prune --json` после удаления ролика из
  папки — удалены он и файл, положенный раньше с `--into big`; сервер отвечает на него 404.
- Память: отправка одного ролика в 20 МиБ — пик RSS 162 МБ при 155 МБ у `cms info` на той же базе (рантайм и
  встроенный менеджер), то есть +7 МБ: файл целиком в памяти не лежит. Отправка всей папки с нарезкой вариантов
  картинки 2048×2048 — 174 МБ.

## Где что

- `src/workspace/media.ts` — `readMediaFolder(dir, into)` (обход, правила, `media.json`), `pushMedia(services,
  folder, { prune, dryRun })`, `parseInto`; экспорт — из `src/workspace/index.ts`.
- `src/cli/commands.ts` — `cms media push`, справка — `src/cli/help.ts`.
- `src/platform/body.ts` — `openFile`: файл как `BodyBytes`, окнами, без удаления при закрытии.
- `src/platform/paths.ts` — `isJunk`, общий с `scaffolds/package/read.ts`.
- Медиатека отдаёт наружу `mediaHash`, `checkSize`, `parseAlt`, `variantWidth`.
- Тесты — `tests/media-push.test.ts`.

## Последствия

- Медиатеку сайта можно держать в git и раскатывать на базу разработки и на боевую одной командой; повтор
  дешёв: совпавшие файлы только читаются для хэша.
- Каждый запуск читает все файлы папки того же размера, что и в медиатеке, чтобы сверить хэш: 96 МБ — доли
  секунды на SSD. Кэша хэшей по времени изменения нет: время после `git checkout` ничего не значит.
- Прерванная отправка оставляет часть файлов новыми — это видно в отчёте, и повтор доводит до конца. Медиатека
  при этом целостна: каждый файл записан своей транзакцией целиком.
- `--prune` не удалит файл, на который ссылается текст страницы, настройка или элемент, даже если владелец этого
  хочет: такой файл удаляют в менеджере, где о ссылках спрашивают.
- Файл, на который ссылаются только переводы или свои настройки сайта, `--prune` не видит и удалит; это те же
  места, которых не видит и менеджер перед удалением.
