# 0049. Windows: сборки x64 и arm64, install.ps1 и замена работающего cms.exe

- Статус: принято
- Дата: 2026-11-03
- Дополняет [ADR 0023](0023-releases-and-installer.md): там «Windows нет: установщик — на bash».

## Контекст

Bun собирает бинарник под Windows с Linux (`--target=bun-windows-x64` и `bun-windows-arm64`), и такая сборка
под wine отдавала страницы, менеджер, медиа и кэш на диске. Значит, препятствие не рантайм, а всё вокруг:
релиз, установщик, обновление, имя команды и места в коде, где молча подразумевался Linux. Часть ограничений
задаёт сама Windows:

- запущенный `.exe` нельзя ни удалить, ни перезаписать, но можно переименовать, в том числе через жёсткую
  ссылку на тот же файл;
- символьная ссылка требует прав администратора или режима разработчика;
- прав POSIX нет, `chmod` меняет только атрибут «только чтение»;
- SIGTERM не приходит, остановка — Ctrl+C, Ctrl+Break или закрытое окно консоли;
- `--windows-icon`, `--windows-title` и прочие сведения о файле Bun вписывает, только когда собирает на самой
  Windows: с Linux — «only available when compiling on Windows». Без отказа вне Windows работает лишь
  `--windows-hide-console`.

## Решение

### Сборки

`scripts/release.ts` знает цели `windows-x64` и `windows-arm64`, файлы — `cms-windows-<процессор>.exe`. Релизные
собирают раннеры GitHub своей архитектуры: `windows-latest` и `windows-11-arm` (репозиторий открытый). Там же
проходит пробный запуск: `bun scripts/release.ts smoke` вызывает `cms.exe version`, поднимает сервер на временной
базе и свободном порту, ждёт 200 на `/_cms/health` до 60 секунд, проверяет, что первый скрипт менеджера приходит
скриптом, а не index.html (так видно, что SPA вшита под своими путями), и останавливает сервер. Сборка с Linux или
macOS тоже работает, только без значка и сведений о файле, и скрипт об этом пишет: для проверки её хватает, в
релиз она не идёт. Байткод — как у остальных целей.

**Значок** берётся только из `manager/static/favicon.svg`; копии ICO в репозитории нет. `scripts/icon.ts`
рисует каждый размер (256, 128, 64, 48, 32, 24, 16) из SVG заново через resvg, собранный в WebAssembly
(`@resvg/resvg-wasm` 2.6.2, зависимость разработки, MPL-2.0), и складывает ICO: 256 — PNG, остальные — 32-битный
BMP с альфой и маской, как значки хранит сама Windows. Выбор против ImageMagick или librsvg на раннере Linux:
версия закреплена в `bun.lock`, файл побайтно один на Linux, macOS и Windows (проверяет
`tests/release.test.ts`), не нужен ни `apt-get`, ни отдельный job с артефактом — значок рисуется прямо на раннере
Windows перед сборкой.

Кадр 256 стоит в ICO первым не случайно. Bun кладёт кадры на места ICON 1…7 и добавляет свою группу значков, а
прежняя группа бинарника Bun (`IDI_MYICON`) остаётся в файле и ведёт на ICON 1. Проводник берёт первую группу,
поэтому на месте ICON 1 должен быть самый крупный кадр: иначе большой значок вышел бы растянутым из 16×16.

**Сведения о файле** (`scripts/binary.ts`, `windowsInfo`):

| Поле Windows                    | Значение                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------- |
| ProductName (`--windows-title`) | `Eile`                                                                           |
| FileDescription                 | `Eile CMS` — так процесс называет «Диспетчер задач»                              |
| CompanyName                     | `Eile contributors`                                                              |
| FileVersion, ProductVersion     | четыре числа из `package.json`: `0.1.0-alpha.9` → `0.1.0.9`, `1.2.3` → `1.2.3.0` |
| LegalCopyright                  | `© <год сборки> Eile contributors, GPL-3.0-or-later`                             |

Полная версия с меткой пре-релиза — у `cms version`: в четыре числа она не помещается.

### Архив — `.zip`, а не `.gz`

В релиз идёт `cms-windows-x64.zip` и `cms-windows-arm64.zip` с одним файлом `cms.exe` внутри, около 61 и 56 МБ.
`.zip` открывает Проводник любой Windows, а `.gz` — только Windows 11 с 23H2, и распаковался бы он в
`cms-windows-x64` без `.exe`: заголовок gzip от Bun имени файла не несёт. `install.ps1` распаковывает zip
встроенным `Expand-Archive`.

Bun zip не читает и не пишет, поэтому в `src/platform/zip.ts` — ровно нужное: файлы deflate (raw,
`Bun.deflateSync` с `windowBits: -15`) или без сжатия, CRC32 — `Bun.hash.crc32`, без ZIP64 и шифрования. Им
упаковывает `pack` и распаковывает `cms update`. Архивы проверены `unzip -t`, 7-Zip и Info-ZIP в обе стороны.

### `install.ps1`

```powershell
irm https://github.com/a-sharapov/eile/releases/latest/download/install.ps1 | iex
& ([scriptblock]::Create((irm https://github.com/a-sharapov/eile/releases/latest/download/install.ps1))) -Version v0.2.0
```

Повторяет `install.sh`: версия — параметром `-Version` или `CMS_VERSION`, каталог — `-InstallDir` или
`CMS_INSTALL_DIR`, ещё `CMS_NO_MODIFY_PATH`, `CMS_REPO` и `CMS_DOWNLOAD_URL` (https или `file://`, http — отказ).
Процессор — по `Win32_ComputerSystem.SystemType`: x64-PowerShell под эмуляцией на ARM видит AMD64, а родная
сборка быстрее. Скачанный архив сверяется с `SHA256SUMS`, `cms.exe version` пробно запускается до замены.
Каталог по умолчанию — `%LOCALAPPDATA%\Programs\Eile`, прав администратора не нужно. `PATH` пользователя
правится в реестре как есть, без раскрытия `%USERPROFILE%`: `[Environment]::SetEnvironmentVariable` записал бы
раскрытое значение строкой REG_SZ. В окне, где шёл `irm | iex`, `cms` работает сразу.

- **Только ASCII.** Windows PowerShell 5.1 декодирует ответ `irm` как ISO-8859-1, а файл без BOM — в кодовой
  странице ANSI. UTF-8-кириллица там превращается в знаки кавычек и управляющие символы и может сломать разбор.
  Поэтому весь файл, комментарии тоже, по-английски, и это исключение из правил стиля; держит его
  `tests/install-ps1.test.ts`. `cms` дальше говорит на языке системы: на Windows без `LANG` язык берётся из
  региональных настроек (`Intl`, ICU берёт их у Windows).
- **В сеансе пользователя.** `iex` выполняет скрипт в окне пользователя, поэтому всё — в одной функции, а
  `$ErrorActionPreference` и `$ProgressPreference` меняются только в ней. `exit 1` — лишь у запуска файлом:
  в окне PowerShell он закрыл бы окно.
- Публикуется рядом с `install.sh`; `pack` вписывает адрес репозитория вместо метки так же.

**SmartScreen и Defender.** Бинарник не подписан. Файл, который скачал PowerShell (`irm`, `Invoke-WebRequest`),
не получает Mark-of-the-Web (поток `Zone.Identifier`), и SmartScreen его не спрашивает. Архив, скачанный
браузером, метку получает, Проводник при распаковке передаёт её `cms.exe`, и двойной щелчок покажет «Windows
защитила ваш компьютер» → «Подробнее» → «Выполнить в любом случае»; снять метку — `Unblock-File cms.exe`.
Smart App Control в Windows 11, если включён, неподписанный файл не пустит вовсе. Defender проверяет 120 МБ при
первом запуске, это несколько секунд. Подпись кода (Azure Trusted Signing, SignPath для открытых проектов) —
следующий шаг, в этот ADR не входит.

### `cms update` на Windows

`buildTarget` знает `win32` → `windows-x64` и `windows-arm64`, архив — `cms-<цель>.zip`.

Замена работающего файла — переименованием:

1. новый файл пишется рядом, `.cms.new.<pid>.exe`, и пробно запускается;
2. прежний `cms.old.exe`, если он есть, удаляется, а если он ещё запущен (сервер, который не перезапускали с
   прошлого обновления), уходит в сторону: `.cms.old.exe.<uuid>.trash`;
3. работающий `cms.exe` переименовывается в `cms.old.exe` — это Windows разрешает;
4. новый файл встаёт на место `cms.exe`; не встал — `cms.old.exe` возвращается обратно.

Имя прежней версии одно на всех системах — `<имя>.old` перед расширением: `cms.old` на Linux и macOS,
`cms.old.exe` на Windows. Расширение остаётся последним, иначе Windows файл не запустит. На Linux и macOS всё по-
прежнему: копия в `cms.old` и замена одним атомарным `rename`. На Windows между двумя переименованиями `cms.exe`
нет долю секунды — атомарной замены запущенного файла Windows не даёт.

Остатки `.trash` удаляет следующий `cms update` (и `install.ps1`); что ещё запущено, подождёт. `restorePrevious`
на Windows так же уводит запущенный файл в сторону и ставит копию `cms.old.exe`. Всё это — через порт
`InstallFiles` (`src/contexts/upkeep/infrastructure/installer.ts`): тесты подставляют каталог с правилами Windows
(запущенный файл не удалить, переименовать можно) и проверяют замену, откат, остатки и второе имя на любой
системе. `cms service` на Windows нет, поэтому перезапуска служб и отката по `/_cms/health` там нет: `cms update`
говорит перезапустить сервер.

### Второе имя `eile.exe` — жёсткая ссылка

Символьная ссылка требует прав администратора или режима разработчика, копия — 120 МБ, которые `cms update`
пришлось бы держать в согласии. Остаются жёсткая ссылка и обёртка `eile.cmd`. Обёртка не годится для сервера: на
Ctrl+C `cmd` спрашивает «Завершить выполнение пакетного файла?», а `%*` портит аргументы с `&`, `^` и `%`.
Жёсткая ссылка прав не требует (NTFS; на FAT и exFAT установщик предупредит и обойдётся без неё), занимает места
ноль, и `argv0` у неё — `eile`: справка и подсказки говорят `eile …`.

Ссылка держит тот файл, на который её сделали, поэтому после замены `cms.exe` её ставят заново: и `install.ps1`,
и `cms update`. Старая ссылка — это запущенный прежний файл, её не удалить, и она тоже уходит в `.trash`; места не
занимает, это тот же файл, что `cms.old.exe`. У жёсткой ссылки свой `process.execPath`, поэтому `eile update`
находит рядом `cms.exe` и обновляет его, если это тот же файл (`installedBinary`, сравнение `ino`). Чужой
`eile.exe` не трогается — ни установщиком, ни обновлением.

### Код под Windows

Что нашлось и исправлено:

- **`Bun.Glob` отдаёт пути через `\`.** `cms elements push` и `check` на Windows не видели ни одного файла папки
  (всё «нет в папке»), а бинарник, собранный на Windows, вшил бы SPA менеджера под ключами `/_app\immutable\…`.
  `posixPath` (`src/platform/paths.ts`) — в папке элементов, в таблице SPA для разработки и в `scripts/binary.ts`.
- **Переводы строк.** `cms elements` читает файлы с LF и без BOM: git с `core.autocrlf` выдаёт CRLF, а без
  этого каждый файл казался бы изменённым и CRLF уходил бы в базу. `pull` пишет LF и не переписывает файл, который
  отличается только переводами строк.
- **Отказ `Bun.file(…).text()` и чтение `Bun.stdin` не держат цикл событий** у Bun для Windows: процесс выходил
  с кодом 0, ничего не сделав. Так молча не работали первый `cms elements pull` в пустую папку и
  `cms users add|password --password-stdin`. Нашлось под wine; на настоящей Windows не проверено, но обход
  годится везде: папка читается через `node:fs/promises`, stdin — потоком (`readStdin` в `src/cli/prompt.ts`).
  Остальные чтения `Bun.file` в командах сначала проверяют `exists()`, а в сервере цикл держит сам `Bun.serve`.
- **Имя команды.** `programName` отрезает каталог по обоим разделителям и `.exe`, регистр не в счёт:
  `C:\…\eile.exe` и набранное `eile` дают `eile`.
- **Остановка.** Сервер ждёт SIGINT, SIGBREAK и SIGHUP (закрытое окно консоли) и, как на Linux, пишет остаток
  статистики и закрывает базу. Обёртки служб вроде WinSW и NSSM останавливают процесс через Ctrl+C.
- **`cms service`** на Windows сразу отвечает, что ставит службу systemd, а её здесь нет, и ссылается на README:
  там планировщик заданий и WinSW.
- **`.gitattributes`** держит LF и на Windows: Biome проверяет LF, а раннеры GitHub на Windows настроены с
  `core.autocrlf`.

Проверено и оставлено как есть:

- пути `--db` с буквой диска, `join` и `dirname` в остальном коде — `node:path` под Windows; строк путей,
  склеенных через `/`, в коде файлов нет (есть пути URL и модулей, им так и надо);
- `file://` в коде — только у адреса установщика (`CMS_DOWNLOAD_URL`) и в проверке ленты релизов;
- переименование поверх файла: кэш медиатеки пишет новую версию под новым именем (хэш содержимого), автокопии —
  в новое имя с датой; если переименование всё же не удастся, кэш, как и на Linux, минуту отдаёт файлы из базы.
  Восстановление копии идёт через `ATTACH` в ту же базу, без переименования открытого файла;
- `Bun.Image`: JPEG, PNG и WebP на Windows — те же статически собранные кодеки, что на Linux; варианты 480, 960
  и 1920 под wine нарезаны и отданы;
- цвет и UTF-8 в консоли: цвет — только в TTY, `NO_COLOR` и `FORCE_COLOR` — как везде; escape-
  последовательности понимают Windows Terminal и консоль Windows 10 и новее. Кириллица и рамки MOTD под wine
  выводятся верно, вид в настоящей консоли не проверен;
- **права файлов.** `chmod 600` у копий сайта и файла настроек сервера (в них хэши паролей и ключи) на Windows ничего
  не делает: доступ задают ACL, наследуемые от папки. В профиле пользователя (`%LOCALAPPDATA%`, «Документы») их
  читают только он, SYSTEM и администраторы; в общей папке вроде `C:\sites` закройте её сами (`icacls`).

### CI

- `.github/workflows/ci.yml`: job `windows` на `windows-latest` — `bun test` целиком (кроме Biome, типов и
  проверки менеджера: от системы они не зависят). Тесты, которым нужен sh или systemd (`install.sh`, перенос базы
  в службу, замена бинарника-скрипта), на Windows пропускаются: замену там проверяет `installer.test.ts` с
  правилами Windows. Права POSIX проверяются только вне Windows (`expectMode`). Таймаут теста — 30 с: отказ
  соединения с закрытым портом Windows сообщает после повторов, а не сразу. Job `check` разбирает `install.ps1`
  парсером PowerShell 7 с раннера Ubuntu.
- `.github/workflows/release.yml`: job `windows` (матрица x64 и arm64) — сборка, пробный запуск, проверка
  сведений о файле, `install.ps1` из `file://` с правкой `PATH`; `publish` ждёт его и выкладывает `.zip` и
  `install.ps1`; `windows-from-release` после публикации ставит одной строкой через Windows PowerShell 5.1.
  Jobs Linux и macOS не менялись.

## Проверено под wine

wine 11.20 staging, сборка x64 с Linux и сборка с значком и сведениями о файле, которую собрал Bun для Windows
под wine (`--windows-*` там работают). Копия живого сайта (42 МБ): страницы, менеджер, вход, загрузка JPEG через API
и три варианта WebP, кэш медиатеки; `cms users add --password-stdin` (после исправления), `elements pull`,
`check` и `push` с файлами в CRLF, `backup`, `restore` в остановленную базу и в базу работающего сервера, Ctrl+C
с записью статистики и без оставленного WAL. `cms update` и `eile update` с ленты на `CMS_RELEASES_URL`: при
работающем сервере на `cms.exe`, при сервере на `cms.old.exe` (ушёл в `.trash`) и третьим разом — уборка
остатков; wine запрещает удалять запущенный файл, как Windows. `scripts/release.ts pack` и `smoke` — тоже под
Bun для Windows. `bun test` под wine: 1472 теста проходят; не проходят `install.ps1` (PowerShell под wine нет),
четыре ожидания отказа соединения (wine его не сообщает) и один тест STARTTLS.

## Что проверит только CI

Сборка и запуск на `windows-11-arm` (под wine — только x64), `install.ps1` целиком (PowerShell под wine не
запускали) и `irm | iex` с настоящего релиза, вид значка в Проводнике, `bun test` на настоящей Windows,
поведение SmartScreen.

## Последствия

- Две цели и два файла релиза больше; `SHA256SUMS` — общие для `.gz` и `.zip`.
- `cms update` на Windows оставляет рядом `cms.old.exe` и иногда `.trash` до следующего обновления.
- Службы Windows нет: сайт держит планировщик заданий или обёртка вроде WinSW (README, «На Windows»).
- Неподписанный бинарник: браузерная загрузка встречает SmartScreen, Smart App Control не пускает.
