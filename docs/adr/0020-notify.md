# 0020. Уведомления: Telegram, почта и сбои сайта

- Статус: принято
- Дата: 2026-10-30

## Контекст

Заявки с форм (ADR 0021) должны доходить до людей, а о сбоях сайта владелец должен узнавать раньше
посетителей. В Evo письма отправляет eForm через PHPMailer, а ошибки остаются в журнале событий. CMS —
один бинарник без зависимостей, кроме `svelte`, поэтому ни nodemailer, ни отдельного бота не будет.
Сервер в России часто не достаёт до api.telegram.org напрямую.

## Решение

Контекст `notify` — каналы, очередь отправки и сбои. Транспорт встроен в сайт, настройки — во вкладке
«Уведомления» в настройках менеджера.

**Каналы — на нативных средствах Bun.**

| Канал    | Как                                                                                                                                                                                                                                                                                                                                                            |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Telegram | Bot API по `fetch` через `Bun.FetchSession`: соединения живут между отправками, у сессии — свой прокси (`http://host:port`), пусто — из `HTTPS_PROXY`. `parse_mode: HTML`, текст экранирует `Bun.escapeHTML`, длинное режется по 4000 знаков. Чаты не вписываются руками: «Найти чаты» берёт их из `getUpdates`, webhook не нужен — сервер может стоять за NAT |
| Почта    | SMTP на `Bun.connect`: TLS сразу (465) или `socket.upgradeTLS` после STARTTLS (587) с проверкой сертификата; вход PLAIN или LOGIN; письмо — multipart/alternative, тела в base64 (`Uint8Array.prototype.toBase64`), темы и имена — словами RFC 2047, `Message-ID` из `Bun.randomUUIDv7()`; переводы строк в значениях заголовков вырезаются                    |

Подводные камни сокетов Bun 1.4 учтены (проверено, скилл `bun`):
- после `upgradeTLS` прежние обработчики получают шифротекст — читается только текущий сокет;
- ошибка сертификата не отклоняет `connect`, её ловит `handshake`;
- `socket.timeout` — срок, а не простой, и взводится на каждую команду;
- у подключения свой срок — 15 с.

Ошибки `fetch` несут полный адрес с токеном бота: токен вырезается до записи в журнал, редиректы
запрещены.

Отказ канала — постоянный (Telegram 400/401/403, SMTP 5xx, нет STARTTLS) или временный (сеть, таймаут,
Telegram 429 с `retry_after`, SMTP 4xx).

**Очередь отправки** (`notify_outbox`). Уведомление ставится синхронно — строкой на адресата — и
отправляется после ответа посетителю. Паузы между попытками: минута, 5 и 30 минут, 2 и 12 часов, потом
отказ; Telegram может попросить ждать дольше. Очередь гоняет `Bun.cron` раз в минуту и сразу после
постановки; задания не наслаиваются, ошибка внутри не роняет процесс. После перезапуска очередь
продолжается, «висящих» строк нет. В менеджере видно недоставленное с настоящей ошибкой канала и кнопкой
«Отправить ещё раз». Отправленное хранится 30 дней.

**Сбои.** Порт `Report` (`shared/kernel/report.ts`) объявляют контексты, связывает его корень композиции.

| Источник                                                                              | Важность |
| ------------------------------------------------------------------------------------- | -------- |
| 500 публичного сайта                                                                  | critical |
| Уведомление не доставлено — сообщается другим каналом                                 | critical |
| Регион или остров не отрисовался, плагин упал, расписание публикаций, 500 менеджера   | error    |
| Перебор пароля к менеджеру; перезапуск без штатной остановки (метка `notify_runtime`) | warning  |
| Новый пользователь менеджера, смена роли, удаление                                    | info     |

Одинаковые сбои — по первой строке ошибки, а не по адресу — за 15 минут склеиваются: первый уходит
сразу, следующий после окна — с «повторялось N раз». Больше 20 уведомлений о сбоях в час не уходит: одно
«сбоев слишком много» и тишина до конца часа. Ниже порога важности (по умолчанию «ошибки») — только журнал
сбоев за 30 дней. Отчёт о сбое синхронный и никогда не бросает. О недоставленном сообщении о сбое — только
журнал: иначе отказ канала порождал бы новые сообщения о себе.

**Маршруты.** Заявки и сбои — в выбранные каналы; форма может задать свои.

**Секреты.** Токен бота и пароль SMTP в менеджер не возвращаются: пустое поле — прежнее значение, пароль —
только для того же сервера и логина. Таблицы `notify_*` — настройка этого сервера: в копию сайта не
попадают и при восстановлении остаются свои.

## Последствия

- Фоновая отправка — только у `cms serve` (`background: true`); команды CLI и тесты гоняют очередь
  сами, тесты подменяют каналы (`transports`).
- `Bun.secrets` (хранилище ключей ОС) не подошёл: на сервере без D-Bus его нет.
- Канал без настроек ничего не ставит в очередь: заявка всё равно сохраняется.
- Новые события шины `notify` не публикует — кэш страниц от уведомлений не сбрасывается.
