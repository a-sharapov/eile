# 0023. Релизы на GitHub и установщик одной строкой

- Статус: принято
- Дата: 2026-10-31

## Контекст

CMS поставляется одним бинарником (ADR 0001), но собрать его можно было только из исходников:
`bun install` и `bun run build` под свою машину. Владельцу сайта на VPS нужен готовый файл под его систему и
простой способ его поставить и обновить — как у Bun, Deno и подобных инструментов. Владелец выбрал
GitHub Releases как источник и установщик, который ставит только бинарник: служба systemd описана в
README, но не создаётся сама.

## Решение

**Цели релиза** — `scripts/release.ts`, `bun build --compile --target`:

| Файл                                         | Платформа                    |
| -------------------------------------------- | ---------------------------- |
| `cms-linux-x64`, `cms-linux-arm64`           | Linux на glibc               |
| `cms-linux-x64-musl`, `cms-linux-arm64-musl` | Alpine и другие на musl      |
| `cms-darwin-x64`, `cms-darwin-arm64`         | macOS: Intel и Apple Silicon |

- Windows нет: установщик — на bash. На x64 Bun даёт один бинарник для всех процессоров, вариант
  `baseline` не нужен.
- Бинарник весит около 115 МБ, в релиз идёт сжатая копия `.gz`, около 54 МБ. В `SHA256SUMS` — суммы
  сжатых файлов.
- Сборке для musl нужны `libgcc` и `libstdc++`: в голом Alpine бинарник не запускается. Установщик
  проверяет их до скачивания.
- Бинарники macOS собираются на раннере macOS и подписываются ad-hoc с правами на JIT
  (`scripts/entitlements.plist`), иначе Apple Silicon их не запустит. Файл, скачанный `curl`, не получает
  карантина, поэтому Gatekeeper его не спрашивает. Подпись Developer ID и нотаризация понадобятся, если
  файл начнут скачивать браузером.

**Workflow** `.github/workflows/release.yml` по тегу `vX.Y.Z`:
1. проверка: тег совпадает с версией, `bun run check`, shellcheck;
2. сборка Linux и macOS параллельно, пробный запуск каждой платформы, которую раннер может выполнить;
3. упаковка;
4. установщик ставит собранное из `file://`;
5. `gh release create`.

Тег с дефисом — пре-релиз, на него не указывает `releases/latest`; но пока стабильных релизов нет, альфы и
беты публикуются обычными, чтобы установка одной строкой работала с первого релиза. На каждый push и pull request
`.github/workflows/ci.yml` повторяет проверку.

**Установщик** `install.sh`:

```sh
curl -fsSL https://github.com/a-sharapov/eile/releases/latest/download/install.sh | bash
```

- Адрес репозитория вписывает в копию скрипта сборка релиза (`pack --repo`). В исходниках стоит метка,
  поэтому скрипт из репозитория просит `CMS_REPO` и не качает чужое.
- Всё тело — в функциях, вызов — последней строкой: оборванная загрузка не выполнит полскрипта.
- Платформа определяется по `uname`, Rosetta, `ldd` и `/etc/alpine-release`.
- Сумма сверяется с `SHA256SUMS`. Новый бинарник запускается (`cms version`) до замены старого, поэтому
  несовместимая система не оставит владельца без работающего `cms`.
- Замена атомарна: временный файл в том же каталоге и `mv`. Работающий сервер доживает на старом файле
  до перезапуска.
- Каталог: `~/.local/bin`, под root — `/usr/local/bin`. Если каталога нет в `PATH`, он дописывается один
  раз в файл оболочки (bash, zsh, fish, иначе `.profile`).
- Рядом с `cms` — символьная ссылка `eile` на него. Чужой файл `eile` в каталоге установщик не трогает и
  предупреждает. `bun run build` тоже кладёт рядом с `dist/cms` ссылку `dist/eile`.
- Настройки: версия — аргументом или `CMS_VERSION`; `CMS_INSTALL_DIR`, `CMS_NO_MODIFY_PATH`,
  `CMS_DOWNLOAD_URL` (зеркало или `file://` для проверки).

## Последствия

- Команда в `PATH` — `cms`: нейтральное имя, как и весь код; название продукта живёт в `src/product.ts`.
  Если в системе уже есть другой `cms`, установщик предупреждает. Второе имя `eile` выручает, когда `cms`
  занят другой программой.
- Второе имя — ссылка, а не копия: `cms update` заменяет файл по `process.execPath`, а у запуска через
  ссылку это путь самого `cms`. Обновлённый файл виден под обоими именами, `cms.old` лежит рядом с ним.
  Установка старше второго имени получает ссылку при `cms update`, если рядом нет файла с этим именем.
- Справка, подсказки, приветствие сервера и ошибки называют команду так, как её запустили:
  `eile help` пишет `eile new …` (`src/cli/program.ts`, имя — из `process.argv0`). Пути, `cms.old` и
  `cms-<дата>.db` остаются как есть: это имена файлов, а не команды.
- Версия хранится в `package.json` и `src/cli/version.ts`, их сверяет тест; тег сверяет `check-tag`.
- Сборка релиза качает рантаймы Bun под чужие платформы при первом `--target`.

## Дополнение: байткод (0.1.0-alpha.8, 2026-11-03)

Бинарник собирается с `--bytecode --format=esm`: код CMS вшит байткодом JavaScriptCore, при запуске его не
нужно разбирать заново. `--format=esm` обязателен: без него байткод собирается как CommonJS, а входной файл
`.build/entry.ts` ждёт `main.ts` через `await` верхнего уровня.

Замер на сайте с базой 42 МБ (18 страниц, 37 компонентов), одно ядро, одна и та же версия кода:

|                                              | Без байткода  | С байткодом   |
| -------------------------------------------- | ------------- | ------------- |
| `cms version`, Linux x64 glibc               | 91 мс         | 41 мс         |
| `cms info`                                   | 245 мс        | 179 мс        |
| `cms elements check`                         | 265 мс        | 196 мс        |
| Сервер: от запуска до первой страницы        | 773 мс        | 637 мс        |
| `cms version`, Alpine x64 (musl)             | 110 мс        | 33 мс         |
| Сервер на Alpine x64: до первой страницы     | 440 мс        | 320 мс        |
| arm64 musl под эмуляцией qemu: `cms version` | 2366 мс       | 1482 мс       |
| Бинарник Linux x64 / сжатый `.gz`            | 108 / 50,7 МБ | 114 / 53,4 МБ |

Остальное не изменилось: страницы побайтно те же (кроме одноразовых меток форм), компоненты
компилируются на лету как прежде, 3000 запросов в 20 потоков: 1,86 и 1,87 с, память в покое и под
нагрузкой в пределах разброса. Байткод привязан к версии JavaScriptCore, но лежит в том же файле, что и
рантайм, поэтому разойтись они не могут. Сборки под чужие платформы (`--target`) получают байткод так же;
проверены запуском Linux x64 glibc и musl, arm64 musl под qemu; macOS проверяет пробный запуск в workflow.
