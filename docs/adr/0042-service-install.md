# 0042. `cms service`: сайт службой systemd одной командой

- Статус: принято
- Дата: 2026-11-03

## Контекст

Установщик ставит только бинарник (ADR 0023). Дальше на сервере владелец сайта копировал юнит из README,
сам решал, где лежит база, кому она принадлежит и как процессу получить порты 80 и 443. Это три шага с
ошибками, которые видны не сразу: база с владельцем root, служба без права на порт, забытый перезапуск после
`cms update`. Цель продукта — «установил и работает» (docs/vision.md).

Замер на дроплете DigitalOcean в 512 МБ: сайту остаётся около 330 МБ. Без подкачки OOM убил его на загрузке
файла в 21 МБ под нагрузкой, с файлом подкачки в 1 ГиБ он выжил. Сервер встаёт за доли секунды.

## Решение

**Команда** `cms service install` и подкоманды `status`, `logs [-f]`, `restart`, `uninstall`
(`src/cli/service.ts`; без эффектов — `src/cli/systemd.ts`). Два режима:
- `--domain a.de,www.a.de [--email …] [--acme-staging] [--port] [--https-port]` — служба сама держит HTTPS;
- `--trust-proxy [--port N] [--host адрес]` — за nginx или Caddy, по умолчанию на `127.0.0.1:8080`.

Ещё `--from <база>`, `--name <имя>` (по умолчанию `cms`), `--print`, `--force`. Оба режима сразу и ни одного —
отказ: с доменом сервер стоит на краю сам, за прокси `X-Forwarded-*` подделает любой, кто дойдёт мимо прокси.

**Юнит** `/etc/systemd/system/<имя>.service` — чистая функция `renderUnit(plan, language)`:
- `ExecStart=<process.execPath> serve …` — тот бинарник, который запустили; база и кэш — в `Environment`:
  `CMS_DB=/var/lib/<имя>/site.db`, `CMS_MEDIA_CACHE=/var/cache/<имя>`;
- `Type=exec`: `systemctl restart` отказывает, если файл не запустился;
- `Restart=always`, `RestartSec=1`, `StartLimitIntervalSec=0`: после любого сбоя, в том числе OOM, служба
  поднимается через секунду и не бросает попыток;
- `DynamicUser=yes`, `StateDirectory=<имя>`, `CacheDirectory=<имя>` (оба 0700), `UMask=0077`;
- `AmbientCapabilities` и `CapabilityBoundingSet=CAP_NET_BIND_SERVICE` — только если служба слушает порт ниже
  1024; иначе `CapabilityBoundingSet=` пуст;
- за прокси — `--host 127.0.0.1` в `ExecStart` (новый параметр `serve`, `CMS_HOST`): мимо прокси до сервера
  не дойти, `X-Forwarded-*` не подделать;
- `Documentation=` — ссылка на этот ADR: по ней `uninstall` узнаёт свой юнит.

Комментарии юнита — на языке CLI. Юниты сравниваются без комментариев и пустых строк (`sameUnit`): повтор
команды под другой локалью — тот же юнит.

**Песочница.** Что пишет сайт: база, её `-wal` и `-shm`, автокопии и копии «до восстановления» рядом с
базой — всё в `StateDirectory`; сертификаты HTTPS и ключи ACME — в самой базе; кэш медиатеки — в
`CacheDirectory`; временные копии восстановления — в `/tmp`, у службы он свой. Поэтому можно закрыть всё
остальное: `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp`, `PrivateDevices`, `ProtectProc=invisible`,
`ProtectKernel*`, `ProtectControlGroups`, `ProtectClock`, `ProtectHostname`, `NoNewPrivileges`,
`RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6 AF_NETLINK` (netlink — для `getaddrinfo`),
`RestrictNamespaces`, `RestrictRealtime`, `RestrictSUIDSGID`, `LockPersonality`, `RemoveIPC`,
`SystemCallArchitectures=native`, `SystemCallFilter=@system-service`. `systemd-analyze security` даёт 1,7
(«OK»). Чего нет и почему:
- `MemoryDenyWriteExecute` — JIT JavaScriptCore пишет исполняемый код, с этим запретом Bun не работает;
- `PrivateUsers` — право на порт ниже 1024 действует только в исходном пространстве пользователей;
- `ProcSubset=pid` — выгоды мало, а что рантайм читает из `/proc` кроме своего процесса, не проверено;
- `PrivateNetwork`, `IPAddressDeny` — сайту нужны исходящие соединения: ACME, SMTP, вебхуки, релизы.

Запрещённый фильтром вызов получает `EPERM` (`SystemCallErrorNumber`), а не убивает процесс: необязательные
возможности рантайма (pkeys) так просто выключаются.

**Владелец базы при `DynamicUser`.** UID службы временный: systemd выбирает его при запуске, предпочитая
владельца уже существующего `/var/lib/private/<имя>`, так что он стабилен. Каталоги службы systemd держит в
`/var/lib/private/<имя>` (0700) и ставит ссылку `/var/lib/<имя>`; старый обычный каталог `/var/lib/<имя>` он
сам переносит в `private` при первом запуске с `DynamicUser`. Владельца он меняет рекурсивно, только если не
совпадает владелец самого каталога. Отсюда `--from`:
1. каталог — `/var/lib/<имя>` по ссылке, если он есть, иначе новый `/var/lib/private/<имя>` с правами 700 от root;
2. база — снимок `VACUUM INTO` (`backupDatabase`, как у `cms backup`), а не `cp`: у работающего сайта свежие
   записи ещё в WAL;
3. снимок проверяется и доводится до схемы этой версии (`prepareSite`: целостность, журнал миграций,
   отказ на чужой базе и на базе более новой версии), пишется в `.site.db.<pid>.part` и переименовывается в
   `site.db`, права 600;
4. владелец новой базы — владелец каталога: каталог уже принадлежит службе — база тоже ей; каталог root —
   systemd при запуске увидит чужого владельца и поправит всё сам.

Своя база службы `--from` не заменяет — для этого восстановление в менеджере, с копией «до». Снимок — вся
база, с сеансами, ключом ИИ, каналами уведомлений и сертификатами: это переезд сайта на той же машине, а не
копия для чужих рук, как у `cms backup`.

Команды `cms` под root на базе службы (`cms users`, `cms backup`) владельца не ломают: SQLite под root отдаёт
новые `-wal` и `-shm` владельцу базы, а при закрытии последнего соединения удаляет их.

**Проверки до установки** — по фактам машины, оценка без эффектов (`assess`):
- Linux, загруженный systemd (`/run/systemd/system`, `systemctl`), иначе отказ со ссылкой на README;
- бинарник — не из исходников, не в `/home`, `/root`, `/tmp`, `/run/user` (службе их не видно) и с правом
  запуска для всех; иначе отказ с командой `install -m 755 … /usr/local/bin/cms`;
- root; иначе отказ со строкой `sudo <бинарник> service install …` — сам себя команда не повышает;
- порты свободны: на порту встаёт тот же `Bun.serve`, занят — имя держателя из `ss -ltnp`. Занят — отказ;
  nginx, Caddy, Apache и подобные — с подсказкой `--trust-proxy`. Порты работающей службы с этим именем не
  проверяются: их держит она сама;
- домены указывают на адрес этой машины (`Bun.dns.lookup` против адресов интерфейсов, без петли и
  link-local) — только предупреждение: за NAT и с облачным адресом это нормально;
- меньше 1 ГиБ памяти без подкачки — предупреждение с командами для файла подкачки в 1 ГиБ. Подкачку команда
  не создаёт: это решение владельца машины.

**Порядок.** Юнит пишется, только если он новый или другой (другой — только с `--force`), затем
`daemon-reload`, `enable`; `reset-failed` и `restart` — если юнит менялся или служба стоит. Тот же юнит у
работающей службы — ничего не перезапускается.

**Здоровье** — HTTP-запрос к службе с этой же машины (`127.0.0.1` и порт из юнита), любой ответ, ждём до
30 секунд. Нет ответа — последние строки журнала и отказ. Версию работающего процесса знает его файл:
`/proc/<MainPID>/exe version` запускает именно тот бинарник, с которого стартовал процесс, даже если файл на
диске уже заменён. Своего адреса с версией сайт не получает: номер версии посетителям незачем. Ссылку
первичной настройки команда берёт из журнала этого запуска (`_SYSTEMD_INVOCATION_ID`).

**`cms update`.** После замены бинарника под root команда находит в `/etc/systemd/system` юниты, чей
`ExecStart` запускает этот файл (так находится и юнит, написанный руками по старому README), и перезапускает
работающие. Каждая должна ответить и работать на новой версии. `--no-restart` — службы не трогать; без службы
всё как раньше.

Вернуть один бинарник мало: новая версия при запуске применяет свои миграции, а они бывают необратимыми
(в 0.1.0-alpha.8 `media/005` и `forms/004` переносят файлы в таблицы частей и удаляют `media_files.data`).
Прежний бинарник на такой базе запустился бы «нормально» и ломался на каждом чтении медиатеки. Поэтому
обновление со службой — так (`restartServices`):
1. **Снимок до перезапуска.** База каждой службы — из юнита (`CMS_DB`, путь без ссылок: `/var/lib/<имя>`
   ведёт в `/var/lib/private/<имя>`). Снимок — `VACUUM INTO` (`backupDatabase`) рядом с базой:
   `site.db.before-<прежняя версия>`, права 600, владелец — как у базы; прежний снимок удаляется, остаётся
   один. Снимки всех служб снимаются до первого перезапуска. Не снялся хоть один (кончилось место, в юните
   нет `CMS_DB`) — ни одна служба не перезапускается, `cms.old` возвращается на диск: работающие процессы и
   файл снова одной, прежней версии, иначе следующий перезапуск (сбой, перезагрузка) применил бы миграции без
   снимка. Команда говорит почему и выходит с кодом 1.
2. **Перезапуск и проверка** — как раньше: ответ по HTTP и версия процесса через `/proc/<MainPID>/exe`.
   Удалось — снимок остаётся, его путь — в итоге команды.
3. **Откат.** Все службы останавливаются (`systemctl stop`: с `Restart=always` новая версия иначе
   перезапускалась бы, пока мы сравниваем). Миграции базы (`_migrations`) сравниваются с миграциями снимка;
   у базы есть новые (или её не прочесть) — база возвращается к снимку: подготовленная копия снимка с
   владельцем и правами базы встаёт на место одним переименованием, а база, на которой новая версия упала,
   — жёсткой ссылкой `site.db.failed-<новая версия>` вместе со своими `-wal` и `-shm`. Так рядом с
   возвращённой базой не остаётся чужого WAL, а записанное после снимка не пропадает: команда называет окно —
   от снимка до возврата — и файл, где эти записи. Базу без новых миграций откат не трогает. Затем `cms.old`
   — на место (`restorePrevious`), службы запускаются и проверяются на прежней версии. Откат касается всех
   служб этого бинарника, и тех, что на новой версии поднялись: их базы тоже успели перейти на новую схему.

**Прежняя версия на базе новой не запускается.** `migrate()` отказывает (`database.newer`), если в журнале
базы есть миграции, которых эта программа не знает; `createApp` при этом закрывает базу. Сервер, `cms info`,
`cms users` и остальные команды говорят, что базу вела более новая версия, и предлагают обновиться или
вернуть копию «до». Это страховка на случай, который откат не покрыл: `--no-restart`, `cms.old`, поставленный
руками, сервер без службы. Мешать она не может: в `_migrations` пишет только `migrate()` и только миграции
`_MIGRATIONS` или их начало на свежей базе; своих миграций у плагинов и каркасов нет; копию из более новой
версии восстановление по-прежнему отклоняет своим `backup.newer` раньше, чем дойдёт до `migrate()`.

## Последствия

- Сервер — три команды: установщик, `sudo cms service install --domain …`, создать администратора по ссылке.
- Юнит из README остаётся справкой: его печатает `--print`, без root и ничего не меняя.
- Только systemd. На Alpine с OpenRC, в контейнере и на macOS команда отказывает и ведёт в README.
- Чтобы служба запускала новый файл, `cms update` нужен root — как и для записи в `/usr/local/bin`.
- Обновление со службой стоит места: рядом с базой лежит её снимок, после неудачного отката — ещё и база, на
  которой упала новая версия. По одному файлу каждого рода; удалять их можно когда угодно.
- Записи между снимком и неудачным запуском не теряются, но и не возвращаются в базу сами: их переносит
  человек из `site.db.failed-<версия>`, если они нужны.
- Прежняя версия не открывает базу, которую вела более новая, даже если новые миграции безвредны: ясный отказ
  дешевле, чем полуживой сайт.
- Проверено на настоящем systemd 252 (podman, ubi-init): установка с `--from`, владелец при `DynamicUser`,
  песочница, режим `--domain` на 80 и 443, status, logs, restart, повтор установки, uninstall, откат
  `cms update` по подменённой ленте релизов. Снимок и возврат базы при откате проверены на файлах и с
  подменённой машиной, на настоящем systemd — ещё нет.
