# 0040. Почтовый шлюз: письма других сервисов через почту сайта

- Статус: принято; тело — во временном файле, письмо уходит кусками: [0043](0043-large-bodies-memory.md)
- Дата: 2026-11-03

## Контекст

Сайт кухонной студии переезжает на Eile, а рядом с ним живёт платформа — свои сервисы, которым тоже нужно
слать письма. Часть писем платформа отправляла через PHP-релей на старом WordPress: `POST` с токеном и JSON
`{ to, subject, html, text, from, attachments }`, ответ `{ok}`. Вместе с WordPress уходит и релей. Почта у
сайта уже настроена (SMTP в «Уведомлениях», ADR 0020): заводить второй SMTP-ящик и второй релей ради
платформы незачем.

Нужен общий шлюз, а не одна интеграция: любой сервис, которому владелец сайта выдал токен, шлёт письмо
через почту сайта. Клиенты прежнего релея должны перейти, поменяв только адрес и токен.

## Решение

**Почтовый шлюз — часть `notify`.** Почта, её отправитель и SMTP-клиент уже там. Настройки шлюза лежат в
`NotifySettings.gateway`, рядом с `email`, а не внутри него: выключили почту — токены и адрес шлюза
остаются, шлюз отвечает 503. В менеджере шлюз — галочка «Почтовый шлюз» в разделе почты, его поля
сохраняются вместе с уведомлениями. Таблица `notify_settings` — настройка этого сервера, поэтому токены в
копию сайта не попадают.

| Настройка   | По умолчанию | Что делает                                                                    |
| ----------- | ------------ | ----------------------------------------------------------------------------- |
| `enabled`   | нет          | Галочка «Почтовый шлюз»                                                       |
| `path`      | `/mailer/`   | Адрес; отвечает и `/mailer`, и `/mailer/`                                     |
| `tokens`    | —            | Токены с подписями («Plattform»), до 10; выпуск и отзыв — отдельными кнопками |
| `rateLimit` | 15           | Запросов в минуту с адреса клиента; 0 — без предела                           |
| `senders`   | —            | Кроме отправителя почты сайта, клиенту разрешены эти адреса в `from`          |
| `domains`   | —            | Получатели только в этих доменах и поддоменах; пусто — любые                  |

**Контракт — как у PHP-релея**, чтобы клиенты не менялись.

- `POST`, `Authorization: Bearer <токен>`, JSON. `to` — строка, список строк, `{address, name}` или их
  список (адрес читается и из `email`, `Address`, `Email`). `from` — строка или `{name, address}`.
  Вложения — `[{ filename, contentType, contentBase64 | content, contentId?, inline? }]`, не больше 40,
  каждое до 2 000 000 байт после base64. Имя файла — без пути и только `[A-Za-z0-9._-]`, тип — без
  параметров и только вида `type/subtype`, иначе `application/octet-stream`. Пустые, битые и большие
  вложения молча отбрасываются, как в PHP.
- `GET` — документ состояния: `ok`, `checks` (`enabled`, `token`, `sender`, `smtp`), предел, адреса
  методов и подсказка; 200, когда готов, иначе 503. `?probe=1` — ещё подключение к SMTP и приветствие 220,
  без входа: `probe: {ok, latency_ms, error?}`. Ни токенов, ни пароля, ни хоста SMTP, ни адресов почты в
  документе нет, ошибка проверки — кодом (`connect_failed`, `timeout`, `tls_failed`, `unexpected_reply`).

Ответ на `POST` — всегда JSON с `Cache-Control: no-store`; тело ошибки — `{ok:false, error:"<код>"}`.
Порядок проверок: состояние шлюза → предел → токен → тело → отправитель → адресаты, тема, текст → домены.

| Статус | Тело                                                                                                  |
| ------ | ----------------------------------------------------------------------------------------------------- |
| 200    | `{ok:true}` — почтовый сервер принял письмо                                                           |
| 400    | `invalid_json`, `to_required`, `subject_required`, `body_required`, `too_many_recipients` (больше 50) |
| 401    | `unauthorized`                                                                                        |
| 403    | `recipient_not_allowed` — только если заданы домены получателей                                       |
| 405    | `method_not_allowed`, `Allow: GET, POST`                                                              |
| 413    | `too_large` — тело больше 40 МБ                                                                       |
| 429    | `rate_limited`, `Retry-After: 60`                                                                     |
| 500    | `from_misconfigured`                                                                                  |
| 502    | `send_failed` — без текста почтового сервера                                                          |
| 503    | `disabled` (выключен, но с токенами), `smtp_not_ready` (почта не настроена)                           |

**Токены.** Выпускает сервер: `mail_` и 32 случайных байта в base64url. Токен показывается один раз, в
ответе на выпуск; на сервере — SHA-256, подпись, последние четыре знака и время последнего запроса.
Предъявленный токен хэшируется и сравнивается с каждым сохранённым за постоянное время
(`crypto.timingSafeEqual`), без выхода на первом совпадении. Выпустить и отозвать токен можно только
войдя в менеджер: ключ API (ADR 0034) этого не может, как не может выпускать и ключи. Выпуск — сведения в
журнале сбоев.

**Отправитель.** Конверт (`MAIL FROM`) — всегда отправитель почты сайта. В `From` — адрес клиента, только
если это отправитель сайта или адрес из `senders`; иначе адрес сайта. Имя остаётся клиента, его нет —
имя сайта. Так шлюз не подделывает чужих отправителей, а письма проходят SPF и DMARC домена сайта. Если в
`From` другой разрешённый адрес, адрес сайта стоит в `Sender`.

**Письмо.** Текст и HTML — всегда оба: недостающее собирается из другого (как в PHP). Картинки с
`contentId` — рядом с HTML в `multipart/related` (их видно по `cid:`), остальные файлы — в
`multipart/mixed`. Заголовки — те же правила, что у уведомлений: значения в одну строку, не ASCII — словами
RFC 2047; адреса проверены и без пробелов, скобок и управляющих знаков. Отправляет тот же SMTP-клиент
(`EmailSender.mail`), у него же проверка связи (`EmailSender.probe`).

**Отправка — сразу, не через очередь `notify_outbox`.**
- Клиент ждёт синхронный ответ, и `{ok:true}` у PHP-релея значил «почтовый сервер принял письмо». Клиенты
  строят на этом свои запасные пути: повторить без вложений, отправить своим SMTP, поставить в свою
  очередь. Ответ «поставлено в очередь» прятал бы постоянные отказы (нет ящика, письмо слишком большое) за
  200, и запасные пути не срабатывали бы.
- Очередь хранит `Message` — уведомление без оформления, а не чужой HTML с вложениями. Письмо шлюза с
  вложениями весило бы до сотни мегабайт в строке очереди, а чужие личные данные лежали бы 30 дней в базе.
- Исчерпанные попытки очереди — критический сбой «уведомление не доставлено» владельцу сайта. О каждом
  неудачном письме чужого сервиса это шум.

Отказ почтового сервера — `502 send_failed` клиенту и предупреждение `notify.gateway_failed` в журнал
сбоев (без адресов из ответа сервера, мимо канала почты). SMTP отвечает и дольше 10 секунд, а по
документации Bun соединение, по которому столько ничего не шло, закрывается и посреди обработки
(`idleTimeout`). Поэтому корень приложения продлевает срок запросу шлюза до 120 секунд (`server.timeout`),
за своим прокси — исходному запросу. Проверено: ответ SMTP через 20 секунд доходит до клиента.

**Адрес.** Сегменты — строчная латиница, цифры, `-` и `_` (не первым), до четырёх; первый — не `manager`
и не `media`. Так шлюзу недоступны менеджер, медиатека, `/_cms/*`, robots.txt и `/.well-known/`.
Маршрут шлюза стоит в корне приложения после служебных адресов и перед сайтом: пока адрес у шлюза, он
перекрывает страницу и переадресацию с тем же адресом — сохранять такой адрес не запрещено, страницу можно
опубликовать и позже. Менеджер показывает перекрытую опубликованную страницу. Адрес у шлюза, пока он
включён или у него есть токены: выключенный шлюз с токенами отвечает `503 disabled`, и клиент видит, что
шлюз выключен, а не получает чужую страницу. Выключенный шлюз без токенов адрес не занимает — `/mailer/`
не отнимается у сайтов, которые шлюзом не пользуются. Адрес шлюза сверяется на каждом запросе, поэтому
настройки `notify` держатся в памяти до записи; запись другим процессом пересобирает контексты
(`data_version`), а с ними и это.

**Предел и журнал.** Окно в минуту на адрес клиента — тот, что дал Bun, а за своим прокси
(`--trust-proxy`) — последний в `X-Forwarded-For`. Считаются все `POST`, с токеном и без, и `GET
?probe=1`: перебор токенов упирается в тот же предел, а простой `GET` — нет, чтобы мониторинг не съедал
предел писем. Каждый `POST` — строка в выводе сервера (`mail-gateway <время> token="Plattform" to=2
files=1 sent`) и в «Последних запросах» менеджера (20 в памяти, с запуска): подпись токена, число
адресатов и вложений, итог. Адресов, темы и текста в журнале нет.

## Последствия

- Клиенту прежнего релея достаточно поменять адрес (`MAIL_HTTP_URL=https://<сайт>/mailer/`) и токен на
  выпущенный в менеджере.
- API менеджера: `GET`/`PUT /notify` несут `gateway` с проверками, последними запросами и перекрытой
  страницей; `POST /notify/gateway/tokens`, `DELETE /notify/gateway/tokens/:id`, `POST /notify/gateway/test`
  — письмо через шлюз на адрес того, кто нажал.
- `EmailSender` получил `mail` и `probe`: подмены каналов в тестах реализуют и их.
- Письмо уходит синхронно и по одному на запрос: медленный почтовый сервер держит запрос клиента до
  ответа SMTP. Повторы — забота клиента.
- Предел и «Последние запросы» живут в памяти процесса: перезапуск и восстановление копии их обнуляют.
