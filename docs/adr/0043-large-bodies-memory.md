# 0043. Большие тела запросов: на диске, а не в памяти

- Статус: принято; размеры картинки при загрузке читаются по первым 256 КиБ, варианты режет сервер:
  [0046](0046-server-image-variants.md)
- Дата: 2026-11-03

## Контекст

Eile ставят и на VPS с 512 МБ памяти. Копию настоящего сайта (база 42 МБ, в медиатеке ролики 21 и 17 МБ)
запустили под `MemoryMax=330M`, так эмулируется такой сервер. Нагрузку из 20 параллельных запросов страниц, 8
скачиваний ролика и пересборки компонентов сервер выдерживал. Под той же нагрузкой его убивал OOM, как только
в менеджер загружали mp4 на 21 МБ. Две загрузки подряд без нагрузки поднимали anon с 88 до 213 МБ, и
обратно память не возвращалась. В почтовый шлюз приходит JSON до 40 МБ с вложениями в base64
([ADR 0040](0040-mail-gateway.md)), в формы — файлы до 20 МБ. Здесь та же беда.

Сначала замеряли, откуда берутся копии, и только потом выбирали решение. Каждый шаг шёл в отдельном процессе
Bun 1.4.4 под своим `systemd-run --scope`, файл — тот самый mp4 на 21 МБ. Память считали по cgroup: `anon` и
`shmem` из `memory.stat`, пик — по `memory.peak`. RSS для этого не годится: страницы одного memfd в двух
отображениях RSS считает дважды.

| Шаг                                                        | Пик, МБ   | Держит после, МБ | Почему                                                                                           |
| ---------------------------------------------------------- | --------- | ---------------- | ------------------------------------------------------------------------------------------------ |

| то же через JS `TransformStream` (счётчик)                 | +11 anon  | 0                | куски проходят через JS                                                                          |

Ответы маленькие (JSON описания файла), копий в них нет. Чего в Bun 1.4.4 нет: `new Response(Bun.file(…)).formData()`
падает с «missing final boundary», у тела запроса нет BYOB-чтения, bun:sqlite не умеет инкрементальный ввод-вывод
BLOB (`sqlite3_blob_*`) и не привязывает `Bun.file` или поток, только TypedArray с копией.

Итог для загрузки через менеджер: пять–шесть копий файла в пике. Последняя привязанная копия жила в
подготовленном запросе медиатеки, отсюда «остаётся навсегда».

В шлюзе на письмо в 36 МБ (14 вложений по 2 МБ) набегало до +475 МБ. Копии делали `.text()` (куски, склейка,
строка), `JSON.parse`, `fromBase64` и сборка MIME: `toBase64()`, потом `match(/.{1,76}/g)` (35 тыс. строк на
вложение), потом `join` на каждом уровне multipart. SMTP-клиент добавлял ещё два `replace`, `encode` и склейку
буфера отправки. Форма с двумя файлами по 15 МБ давала +142 МБ: куски, склейка, memfd FormData, две копии в SQLite
и копия, оставшаяся в запросе.

## Решение

**Тело с файлами ждёт разбора на диске.** Загрузка `POST /manager/api/media` и письмо шлюза пишутся во временный
файл `<кэш медиатеки>/.upload.<uuid>.part`, это `spoolBody` в `platform/body.ts`. Кэш медиатеки и так лежит рядом
с базой, на диске с правом записи ([ADR 0038](0038-media-cache.md)). Для тела с Content-Length файл пишет
`Bun.write(path, new Response(request.body))`, без кусков в JS: больше этой длины Bun.serve не пропустит, а
размер ещё раз сверяется после записи. Тело без Content-Length считается по ходу записи. Потолки и коды
прежние: 32 МБ на маршрут медиатеки (`413 manager.too_large`), 25 МиБ на файл (`422 media.invalid_size`), 40 МБ у
шлюза (`413 too_large`). Временный файл удаляется сразу после разбора. Файл, брошенный упавшим процессом,
удаляет уборка, если ему больше часа. Если кэша на диске нет (база в памяти, кэш после сбоя записи
отдыхает), тело читается в память одним буфером нужной длины (`readBody`).

**Свой разбор multipart** (`platform/multipart.ts`) вместо `formData()`. Части — это диапазоны тела, байты не
копируются. Тело читается окнами по 1 МиБ внахлёст, поэтому разделитель на стыке окон не теряется.
Поведение как у FormData в Bun: часть без имени пропускается, тип файла берётся из заголовка части в нижнем
регистре, без заголовка — по расширению. Заголовки части — не больше 16 КБ. Тип запроса с границей читается
до тела: у запроса, собранного из FormData (инструменты агента), Bun после чтения тела его уже не отдаёт.

**Содержимое медиатеки — куски по 1 МиБ** в `media_chunks`, миграция `media/005_chunks` удаляет колонку
`media_files.data`. Иначе SQLite держит две копии файла на запись (четыре на замену) и одну-две на чтение. Без
кусков загрузка не ужалась бы меньше трёх копий, даже если тело лежит на диске. Куски окупаются и при отдаче.
Выгрузка в кэш на диске идёт по куску. Каждый кусок читается одним запросом вместе с хэшем файла, поэтому
кусок другой версии обрывает выгрузку, и под именем-хэшем другого содержимого не будет. Отдача без кэша
читает по одной строке на кусок ответа, а не весь BLOB на каждые 4 МиБ. `media_chunks` — обычная таблица с
rowid, не WITHOUT ROWID: поиск по `(path, n)` идёт по индексу и не читает BLOB соседних строк. Файл загрузки
служба медиатеки получает как `UploadContent` (`size`, `read(start, end)`) и читает его прямо из временного
файла: окном по 1 МиБ для хэша, по куску для записи. Целиком в память попадает только картинка без
присланных размеров: заголовок JPEG может стоять где угодно.

**Файлы заявок тоже лежат кусками** (`forms_file_chunks`, `forms/004_file_chunks`). Тело формы с файлами
читается одним буфером в памяти, файлы — окна в него.

**Письмо шлюза уходит кусками.** В память тело попадает уже текстом, `Bun.file(…).text()` даёт одну копию.
`mailParts` отдаёт письмо кусками: base64 вложения кодируется блоками по 1024 строки в общий буфер, строки
раздвигаются под CRLF на месте. SMTP-клиент пишет кусок и берёт следующий только после того, как сокет принял
предыдущий. `dotStuffed` удваивает точки и закрывает письмо так же, как это делалось для письма одной строкой,
в том числе на стыке кусков. `mailMime` (письмо строкой) остаётся для тестов и совпадает с прежним байт в байт.
После тела от 4 МБ шлюз дважды зовёт `Bun.gc(true)`: после разбора и после отправки. Разобранное тело держит
только сам вызов отправки, замыкание ответа его не держит.

**Восстановление копии** (`POST /manager/api/backup`) читает тело одним буфером, а не через `_buffered` и
`arrayBuffer()`. Было четыре копии, стала одна.

### Совместимость

- `cms backup`, автокопии и скачивание `.db` — по-прежнему один файл базы.
- Копия `.db` от прежней версии при восстановлении приводится к текущей схеме (`prepareDatabase`), то есть
  проходит `media/005` и `forms/004`.
- JSON-копия (`cms-archive`, версия 1) остаётся общей по таблицам. В новой копии есть строки `media_chunks` и
  `forms_file_chunks`, а в `media_files` и `forms_files` нет `data`. Старая копия с `data` и без новых миграций
  восстанавливается так: схема копии, затем её строки, затем недостающие миграции; содержимое переезжает в
  куски. Это проверяет `tests/backup.test.ts`. Копию новой версии прежняя программа, как и раньше, не
  принимает (`backup.newer`).
- Миграция переносит файл за файлом: страницы, которые освободил один файл, занимают куски следующего. Поэтому
  база вырастает только на самый большой файл. Копия сайта Kuechenly выросла с 44 до 66 МБ, из них 21 МБ —
  свободные страницы. Их займут новые файлы, а `cms backup` (VACUUM INTO) копирует базу без них. Миграция
  выполняется один раз при запуске: 0,25 с, `memory.peak` +138 МБ вместе с кэшем страниц WAL (две-три копии
  самого большого файла).

## Замеры

**Стенд.** Сервер запускается из исходников ветки (`bun src/main.ts --port 8094 --db <копия>`,
`NODE_ENV=production`) под `systemd-run --user -p MemoryMax=330M -p MemorySwapMax=0 -p CPUQuota=100%`. «До» —
код `d3d4d3f` (`git archive`) в том же режиме, «после» — эта ветка на копии, заранее прошедшей миграцию:
миграция — разовая цена, она замерена выше. Копия базы — `sqlite3 … ".backup"` сайта Kuechenly плюс свой
пользователь (`cms users add`). Вход — через `POST /manager/api/session`. Нагрузка — 3000 запросов к 12 страницам
(с `/manager/` и `/index.md`) по 20 параллельно, 8 параллельных скачиваний ролика webm на 17 МБ и
`cms elements push` с изменённым `Layout` (пересборка всех компонентов). Через 0,3 с после старта нагрузки идёт
`curl -F file=@film.mp4` на 21 МБ. Сэмплер раз в 50 мс читает `anon` и состав памяти из `memory.stat` cgroup
юнита. После прогона читаются `memory.events` (`oom_kill`) и `systemctl show -p MemoryPeak -p Result`. Скрипты
стенда в репозиторий не входят.

**База — на диске, не в tmpfs.** Страницы tmpfs — это shmem: без swap их нельзя вытеснить, и они
засчитываются в предел. Первые прогоны в `/tmp` мерили WAL базы (до 80 МБ shmem), а не сервер. Из исходников
одна нагрузка, без загрузки, держит около 300 МБ anon при 330M; при пределе 1G та же нагрузка поднимала anon до
410 МБ, то есть у предела мусор собирается раньше. На загрузку остаётся 5–10 МБ. Поэтому одной копии тела в
памяти не хватило: файл на 5 МБ проходил, а на 11 МБ и на 21 МБ сервер убивал OOM (3 из 3). Так и появилось тело
на диске.

| Сценарий (из исходников, `NODE_ENV=production`)           | До                                                          | После                                                 |
| --------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------- |
| Нагрузка и загрузка 21 МБ, 330M, три прогона              | OOM 3 из 3 (`Result=oom-kill`), загрузка оборвана           | выжил 3 из 3, загрузка 201, пик anon 303–304 МБ       |
| Только нагрузка, 330M                                     | выжил, пик anon 301 МБ                                      | выжил, пик anon 299 МБ                                |

В прогонах «после» загруженный файл в базе совпадает с исходным: 21 кусок, хэш `76ad50e1a708e5e9`, как у
`sha256sum`. `MemoryPeak` в прогонах под нагрузкой равен пределу и «до», и «после»: сервер держится у предела, а
ядро вытесняет кэш страниц. Разница в том, умещается ли anon.

**`Bun.gc()`.** Полная сборка (`Bun.gc(true)`) на прогретом сайте (куча 33 МБ) занимает 4–8 мс; две сборки
удлиняют ответ шлюза на письмо в 36 МБ на 20–35 мс. Асинхронная `Bun.gc(false)` ничего не дала: пик и остаток
те же. Без явной сборки после письма шлюза оставалось +110…+145 МБ мусора, со сборкой память возвращается к
исходной (−1…+25 МБ), пик ниже на 20%.
Для загрузки в медиатеку сборка не нужна: тело лежит на диске, мусора почти нет. Публичному приёму форм она не
нужна тоже: каждый посетитель с файлом в 4 МБ мог бы останавливать сервер на десятки миллисекунд. Поэтому
`Bun.gc(true)` зовёт только шлюз — у него токен — и только после тела от 4 МБ.

## Что не сделано и почему

- **Файлы — в SQLite прямо из потока, без временного файла.** Нужен потоковый разбор multipart и куски под
  временным ключом, которые потом переименовываются. Временный файл проще, а его страницы ядро вытесняет, в
  предел они не упираются.
- **Тела форм — на диск.** Форма публичная: временные файлы от анонимных посетителей — отдельное решение о месте
  на диске. Тело и так в памяти одной копией, файлы — окна в него, в SQLite они идут кусками. Предел — 50 МБ на
  заявку и четыре загрузки одновременно (как было).
- **Потоковый разбор JSON шлюза.** `JSON.parse` нужны текст и результат, это две копии тела на время разбора.
  Разбор с декодированием base64 на лету сложен, а API внутреннее, с токеном и пределом 40 МБ.
- **Свой кодировщик base64 прямо в байты.** Он убрал бы около 36 МБ короткоживущих строк `toBase64()` на письмо
  в 36 МБ, но в 5 раз медленнее встроенного (57 мс против 10 на 27 МБ). Со сборкой после отправки он не нужен.
- **Восстановление копии через API — на диск.** Тело по-прежнему держится в памяти одной копией (было четыре),
  а дальше всё равно пишется во временный файл. Это следующий шаг, если копии вырастут.
- **Экспорт JSON** собирает все строки в памяти, как и прежде. Это другая задача.

## Последствия

- Загрузка в медиатеку держит в памяти около нуля копий файла, а не пять-шесть. Целиком в памяти оказывается
  только картинка без присланных размеров. Памяти после загрузки не прибавляется.
- На диске рядом с кэшем временно лежит тело запроса: до 32 МБ на загрузку, до 40 МБ на письмо шлюза.
- API: `media.uploads.spool`, `MediaCache.spool`. `MediaRepository.piece` и `chunk` заменили `content`.
  `Upload.data` теперь `Uint8Array` или `UploadContent`. `defineNotify` получил `spool`, `EmailSender.mail`
  пишет письмо кусками. В `platform` появились `body.ts`, `multipart.ts` и `chunks.ts`.
- Отдача без кэша идёт кусками по 1 МиБ, а не по 4 МиБ: каждый кусок ответа — одна строка базы.
- База один раз вырастает на самый большой файл медиатеки.
