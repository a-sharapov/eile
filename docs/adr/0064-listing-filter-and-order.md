# 0064. Свой отбор и порядок списка страниц

- Статус: принято
- Дата: 2026-11-08

## Контекст

`listing(parent, options)` (ADR 0019) сортирует только по `published`, `created`, `title` и `menu`, а
отбирать не умеет. Каталогу памятников нужно больше: «товары под страницей 13, у которых в поле
`specification` (хранится как `Эксклюзивные||Цветные`) есть «Цветные», по числовому полю `price` по
возрастанию, по 18, с обычным пейджером». В Evo это DocLister с `&filters` и `&orderBy` по TV. Язык
фильтров DocLister — свой мини-язык в строке; в шаблоне Eile уже есть JavaScript.

Сортировка и отбор по значениям полей в SQL потребовали бы разбирать JSON значений, наследование (`inherit`)
и умолчания в запросе — то, что модель чтения сейчас делает в коде для одной страницы.

## Решение

**Функции в параметрах.** `ListingOptions` получает:

- `filter?: (page: PageView) => boolean` — остаются страницы, для которых он вернул true;
- `order?: (a: PageView, b: PageView) => number` — порядок вместо `sort`, как у `Array.sort`; сортировка
  устойчивая, при равенстве остаётся порядок `sort`;
- `page?: number` — номер порции явно.

**Кандидаты — те же, что у обычного списка.** С `filter` или `order` модель чтения берёт все страницы, что
взял бы обычный список (тот же `WHERE`, `depth`, `includeHidden`), по его сортировке, строит виды с полями,
отбирает и сортирует в JS, затем режет порцию. `total`, `pages`, `pager()`, 404 за последней порцией и теги
кэша (`children:<id>` каждого контейнера) — как раньше. Без функций список идёт прежним путём, по индексу.

**Цена.** Значения полей пачки и её предков читаются одним запросом (`json_each`), а не запросом на
страницу. На gabriel.by у страницы 13 2586 кандидатов и 33 тыс. значений полей: SQL — около 40 мс, разбор
JSON и виды — ещё 30. Поэтому виды кандидатов замораживаются (`Object.freeze`, и `fields` тоже) и держатся
в памяти до любой правки контента или смены стиля адресов, не больше 8 наборов. Первый вызов — около 70 мс,
следующие — около 1 мс: отбор с порядком по запросу посетителя в `Uncached` не собирает ветку заново.

**Явный номер.** Внутри `Uncached` хвоста адреса нет: регион рисуется своей областью рендера без порции, и
`listing()` там всегда на первой порции, а `url(n)` — null. Компонент каталога с сортировкой по запросу
(`?page=3&sort=price-desc`) передаёт номер сам: `page: Number(request().query.page ?? 1)`. С `page` список не
сообщает о себе первой фазе (нет 404), номер за последней порцией становится последним, а `url(n)` и
`pager()` дают тот же путь запроса с `page=N` (остальные параметры сохраняются, у первой порции `page` нет).

## Последствия

- Каталог на Eile пишется одним компонентом без своего SQL и без PHP-сниппета.
- Функции — код шаблона: ошибка в них — ошибка рендера страницы, как любая другая.
- Виды кандидатов только для чтения: попытка поменять `item.title` в шаблоне бросит TypeError.
- Постраничный список только в `Uncached` не даёт адресов `/blog/page-2`: такие адреса — 404; порции там —
  через `page` и query.
