# 0062. Основной домен: остальные имена из `--domain` ведут на первый

- Статус: принято
- Дата: 2026-11-05

## Контекст

С `--domain example.com,www.example.com` (ADR 0028) сервер выпускает один сертификат на все имена и отвечает на
каждом из них. `parseDomains` уже называет первое имя основным, но на деле это мало что значило:

- HTTP-порт вёл на HTTPS того же имени, с которым пришёл посетитель: `http://www.example.com/` →
  `https://www.example.com/`;
- HTTPS-порт отдавал сайт на любом имени.

Сайт открывался и с `www`, и без него. Canonical указывает на основной домен, только если в «Настройках» задан
адрес сайта. Без него canonical, sitemap и ссылки строятся от адреса запроса, и поисковик видит два одинаковых
сайта. Перед Caddy или nginx это решают одной строкой — `redir https://example.com{uri} 308` для www. Без прокси
Eile должна делать то же сама, из коробки.

## Решение

**Основной домен — первый в `--domain`**, как и раньше в `parseDomains`. Дополнительные — все остальные:
`isSecondaryDomain` (домен `certificates`) — имя есть в списке и оно не первое. Точка на конце имени
(`www.example.com.`) не мешает.

**HTTP-порт** (`defineHttpListener`), когда сертификат есть, ведёт на HTTPS основного домена — с любого Host:
с основного, с дополнительного и, как раньше, с чужого. Переход один: `http://www.example.com/a?b=1` →
`https://example.com/a?b=1`, без шага через `https://www.example.com`. Порт HTTPS, если он не 443, остаётся в
адресе. Не меняется:

- ключи HTTP-01 (`/.well-known/acme-challenge/`) HTTP-порт отдаёт сам на любом домене: сертификат на
  дополнительные имена выпускается и продлевается, как раньше;
- пути `direct` (`/_cms/health`) отдаются по HTTP на любом домене;
- пока действующего сертификата нет, HTTP отдаёт сайт на любом домене как есть, на дополнительном тоже.

Последнее — нарочно. Сертификат выпускается на все имена разом, значит, проверка HTTP-01 прошла и для основного:
в момент выпуска его DNS указывал на этот сервер. Без сертификата этого никто не проверял. При переезде DNS
дополнительного имени нередко переключают раньше основного, и переадресация увела бы посетителя на старый сервер
или в никуда.

**HTTPS-порт** (`defineHttpsListener` — обёртка вокруг сайта в `serveSecure`): запрос с Host из дополнительных
доменов получает 308 на тот же путь и query основного, с портом HTTPS, если он не 443. В сайт как есть идут:

- основной домен;
- Host не из списка: IP, `127.0.0.1`, `localhost`, чужое имя. Их и раньше отдавал сайт. IP и `localhost` в
  `--domain` не попадают (`parseDomains`), поэтому запросы с этой машины не переадресуются никогда;
- пути `direct` — `/_cms/health`: монитор, настроенный на `https://www.example.com/_cms/health`, получает ответ, а
  не 308.

Переадресация стоит до сайта: такой запрос не собирает контексты, не запускает расписание публикаций и не попадает
в статистику.

**308, а не 301.** Оба кода постоянные: поисковики переносят адрес одинаково (Google считает 308 равным 301), а
`cms diagnose redirects` принимает оба (ADR 0048). Разница — в методе. На 301 браузер повторяет POST как GET без
тела, на 308 — тем же методом и с тем же телом. С 301 запрос клиента API на дополнительный домен тихо стал бы
GET и потерял данные, с 308 он доходит до основного таким, каким был. Заявку формы Eile, отправленную со
страницы на дополнительном домене, основной не примет: её `Origin` — другое имя (ADR 0021). Посетитель увидит
ошибку отправки, а не пустую страницу. Так бывает только со страницей, открытой до обновления: после него
страницы с формами отдаются уже с основного домена. Тот же 308 HTTP-порт уже даёт при переходе на HTTPS
(ADR 0028), так что правило одно на оба порта. 308 не понимают только очень старые браузеры (IE 11 на Windows 7
и 8.1), но они и так упираются в 308 при переходе с HTTP.

**Браузер помнит переадресацию сутки** (`Cache-Control: max-age=86400` у 308 HTTPS-порта). Постоянную
переадресацию без срока браузер хранит, пока кэш не очистят. Допустим, владелец сменил основной домен —
переставил имена в `--domain`. Тот, кто уже бывал на `www`, получает из своего кэша `www → example.com`, а сервер
теперь отвечает `example.com → www`: петля, «слишком много переадресаций». Со сроком в сутки запись уходит сама.
Переадресации HTTP-порта ведут на `https://`, петли с ними не бывает, и заголовка у них нет, как и раньше.

**Флага, чтобы выключить, нет.** Один процесс — один сайт, и содержимое от имени хоста не зависит: дополнительный
домен может показать только копию основного. Нужные случаи покрыты и так:

- основным должен быть `www` — поставить его первым: `--domain www.example.com,example.com`. Новый сертификат не
  нужен: состояние ищется по набору имён в любом порядке (`domainsKey`);
- нужна другая политика (оба имени без переадресации, 302, свои правила для путей) — свой прокси и
  `--trust-proxy`: имена там решает прокси, Eile их не трогает;
- переезд, пока основной ещё смотрит на старый сервер: сертификата нет — нет и переадресации.

Флаг можно добавить позже, ничего не сломав. Убрать его потом — уже несовместимое изменение.

**HSTS — как было.** Каждый ответ HTTPS-порта, переадресация тоже, несёт `Strict-Transport-Security:
max-age=31536000` (`withHsts`). Браузер запоминает, что и дополнительное имя — только HTTPS, и после первого
визита сам меняет `http://www…` на `https://www…`, без запроса по HTTP. Ответы HTTP-порта, как и раньше, без
него.

**За прокси ничего не меняется.** С `--trust-proxy` без `--domain` у сервера нет слушателей с доменами,
переадресацию делает прокси. `cms service install` эти режимы вместе не принимает. Если `cms serve` всё же
запущен с обоими флагами, TLS держит сам Eile, и имя берётся из Host запроса к нему, а не из `X-Forwarded-Host`.

**Проверка служб.** `cms service install`, `restart` и `cms update` стучатся в
`http://127.0.0.1:<порт>/_cms/health` (ADR 0048): `127.0.0.1` — не домен из списка, а `/_cms/health` — путь
`direct`. Проверки работают, как раньше.

## Последствия

- `--domain example.com,www.example.com` даёт сайт по одному адресу: canonical, sitemap и cookie входа — от
  основного домена, даже если адрес сайта в «Настройках» не задан.
- Менеджер на дополнительном домене открывается переходом на основной, и войти можно только там: cookie
  `__Host-` привязана к имени.
- Клиенты API, MCP по HTTP (`/manager/mcp`) и почтового шлюза (ADR 0040), настроенные на дополнительный домен,
  получат 308. Заголовок `Authorization` при переходе на другой хост браузеры и curl отбрасывают, поэтому таким
  клиентам нужен адрес основного домена.
- Сменить основной домен — переставить имена в `--domain` и перезапустить сервер. У того, кто уже заходил на
  прежний дополнительный, браузер до суток может показывать «слишком много переадресаций», пока старая запись не
  уйдёт из кэша.

## Проверка

- `isSecondaryDomain` — доменный тест рядом с кодом.
- Обработчики обоих портов — в `tests/certificates.test.ts`: с дополнительного домена по HTTP сразу на HTTPS
  основного, одним переходом; по HTTPS — на основной с тем же путём, query, методом и сроком в кэше; основной,
  чужой Host, `127.0.0.1`, `[::1]` и `localhost` — сайт; HTTP-01 и `/_cms/health` на дополнительном — как раньше;
  без сертификата — сайт; порт HTTPS не 443 — в адресе.
- `serveSecure` целиком — с настоящим TLS на сертификате учебного центра (ADR 0028): POST на дополнительный домен
  получает 308 с HSTS, основной отдаёт страницу, `/_cms/health` отвечает на дополнительном по HTTP и HTTPS,
  запрос на `127.0.0.1` идёт в сайт.
