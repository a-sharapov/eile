# 0038. Кэш медиатеки на диске: источник — SQLite

- Статус: принято; содержимое в базе — кусками по 1 МиБ, выгрузка и чтение из базы — по куску:
  [0043](0043-large-bodies-memory.md)
- Дата: 2026-11-02

## Контекст

Медиатека — BLOB в той же базе, что и сайт ([ADR 0001](0001-bun-sqlite-single-binary.md),
[ADR 0015](0015-site-backups.md)): копия сайта — один файл. Но обработчик `/media` на каждый запрос читал BLOB
целиком в память и только потом резал кусок для ответа 206. Видео — до 25 МиБ, браузер читает его десятками
запросов Range: N зрителей занимали около N × размер файла памяти.

Вторая причина нашлась при замерах. `media_files` — таблица `WITHOUT ROWID`, и строка в ней — ключ целиком:
поиск по `path` читает полезную нагрузку и нужной строки, и соседних, с которыми сравнивается. Описание
картинки в 10 байт рядом с видео читалось 2 мс, описание видео — 7–9 мс, и всякий раз внутри SQLite
появлялся временный буфер размером с файл. `substr()` у BLOB тоже сначала поднимает значение целиком.

## Решение

**База остаётся источником, диск — производный кэш.** Копия сайта (`cms backup`, автокопии, скачивание в
менеджере) — по-прежнему только файл базы. Кэш в неё не входит, и его можно стереть в любой момент: он
наберётся заново.

- **Где лежит.** По умолчанию — папка `<база>.media-cache` рядом с файлом базы: `site.db` → `site.media-cache`.
  Рядом с базой уже есть право записи (у systemd это `StateDirectory`), а слово cache в имени говорит
  владельцу, что это не данные. Другая папка — `--media-cache` или `CMS_MEDIA_CACHE`. У базы в памяти
  (тесты, `createApp()`) кэша нет: файлы идут из базы.
- **Имена.** `<папка файла>/<хэш>`:
  - папка — путь файла, где `/` стал `~` (`images~summer~photo.jpg`). В пути медиатеки только латиница, цифры
    и `._@-`, поэтому имя обратимо, не длиннее 255 и не выходит из каталога, а владелец видит, чей это файл;
  - имя — `MediaFile.hash`, хэш содержимого (16 hex SHA-256), тот же, что в ETag и `?v=`. При выгрузке он
    берётся из той же строки, что и содержимое: под этим именем другой версии быть не может.
- **Выгрузка при промахе.** Первый запрос файла читает BLOB из базы, пишет `.<хэш>.<uuid>.part` в ту же папку
  и переименовывает: недописанный файл не отдаётся никогда. Одновременные промахи по одному файлу ждут одну
  выгрузку. Файл кэша сверяется по длине с `size`: другая длина — выгрузка заново.
- **Отдача.** `new Response(Bun.file(…))`, кусок — `Bun.file(…).slice(start, end + 1)` со статусом 206:
  Bun.serve отдаёт файл через sendfile, в память его не читая. Диапазон режет сам обработчик, а не Bun.serve.
  Так ответ одинаков в `app.fetch` (тесты) и в сети, остаются прежние 416 и заголовки, а `Accept-Ranges` не
  двоится: нарезая ответ 200 сам, Bun.serve добавляет свой. Range разбирается так же терпимо, как в Bun.serve
  (единица без учёта регистра, пробелы), иначе тот перерезал бы наш ответ 200.
- **HEAD** — заголовки и длина всего файла, без тела и без выгрузки. Range у HEAD не действует (RFC 9110):
  прежде HEAD с Range отвечал 206, а длина на проводе была 0.
- **Сброс.**
  - `media.file_saved` и `media.file_removed` удаляют прежние версии файла. Текущий хэш остаётся, поэтому
    смена описания файл не трогает. Варианты размеров — свои строки медиатеки, с ними так же.
  - Восстановление копии стирает кэш.
  - Уборка раз в сутки, в 04:15 по часам сервера, — порт `tidy` контекста `upkeep`: файлы и папки, которых
    нет в базе, и недописанные `.part` старше часа. Удаляются только имена в формате кэша, чужие файлы
    остаются, даже если папкой назначен общий каталог.
- **Другой процесс** (`cms mcp`) пишет в ту же базу — сервер пересобирает контексты по `data_version`. У нового
  содержимого новый хэш, значит и новое имя; старый файл уйдёт при уборке. Кэш создаёт корень композиции, один на
  процесс: пересборка его состояние не теряет.
- **Отказ.** Если папку нельзя создать или записать (диск только для чтения, кончилось место) — одна строка в
  журнал, минута без попыток записи, а файлы идут из базы кусками по 4 МиБ: `substr(data, start + 1, length)`,
  длина — из `size`. Готовые файлы кэша отдаются и в это время.
- **Описание файла без BLOB.** Миграция `media/003_covering_indexes` добавляет покрывающие индексы по `path` и
  `stem` со всеми полями описания, запросы идут с `INDEXED BY`: сам планировщик выбирает первичный ключ.
  Описание читается за 0,001 мс вместо 2–9 мс. Таблицу не перестраиваем: это переписало бы всю медиатеку и
  раздуло бы файл базы до VACUUM.

## Последствия

- Память: одна копия на файл, который выгружается прямо сейчас, потом ноль. Без кэша — кусок 4 МиБ на ответ
  плюс временное значение внутри SQLite: `substr` поднимает BLOB целиком, но запросы идут по одному,
  `bun:sqlite` синхронный.
- Первый запрос файла медленнее: чтение из базы и запись на диск. Места на диске кэш занимает не больше, чем
  медиатека в базе.
- Если файл заменили или удалили между ответом обработчика и открытием файла в Bun.serve, этот запрос получит
  500. Окно — микросекунды, и речь о версии, которой уже нет.
- Без кэша большие видео дороги для процессора: каждый кусок читает BLOB целиком, около 14 мс на кусок файла в
  25 МиБ. Это аварийный режим, а не обычный.
- `Last-Modified` по-прежнему нет: браузер сверяется по ETag, как и раньше.
