# 0045. Копии вне сервера, файл настроек сервера и сжатие базы

- Статус: принято
- Дата: 2026-11-03

## Контекст

Живой сайт запускается на одном маленьком дроплете DigitalOcean (512 МБ – 1 ГБ). Автокопии
([ADR 0024](0024-scheduled-backups.md)) лежат на том же диске, а кукбук просит скачивать копии руками. Умрёт диск
или аккаунт — сайт умрёт вместе с копиями.

Настройки сервера в копию сайта намеренно не входят (`_SERVER_ONLY` в `app.ts`): SMTP, Telegram, почтовый шлюз
([ADR 0040](0040-mail-gateway.md)), секрет печатей форм, ключ ИИ. Переезд с ноутбука на сервер (`cms service
install --from`, [ADR 0042](0042-service-install.md)) значит вписать их заново. Живой сайт так и переезжает.

После переноса медиатеки в куски ([ADR 0043](0043-large-bodies-memory.md)) файл базы живого сайта — 63 МБ, из них 21 МБ
— свободные страницы. Копии `VACUUM INTO` компактны, но сам файл не уменьшается никогда.

Eile должна укладываться примерно в 330 МБ: копия в 60–100 МБ не может лежать в памяти несколько раз.

## Решение

### 1. Копии вне сервера (S3)

**Хранилище — любое S3-совместимое через `Bun.S3Client`**: DigitalOcean Spaces, Backblaze B2, Hetzner, MinIO, AWS.
Настройки — «Настройки → Копии и обновления» → «Копии вне сервера»: адрес (пусто — AWS по региону), регион, бакет,
папка в бакете, ключ доступа, бакет в имени хоста (virtual-hosted style), сколько хранить (по умолчанию 14).
Секрет ключа доступа хранится только на сервере, в API не возвращается (`hasSecret`); пустое поле — прежний секрет,
но только для того же адреса, бакета и ключа доступа (как пароль SMTP). Кнопка «Проверить связь» проверяет то, что
в форме, ничего не сохраняя: список с `maxKeys: 1`, запись и удаление пробного объекта `.eile-check`.

Хранилище — контекст `upkeep`: таблица `upkeep_offsite` (миграция `upkeep/002_offsite`) — одна строка JSON с
настройками, секретом, ключом копий и итогом последней отправки. Таблица серверная (`UPKEEP_SERVER_TABLES`): в копию
сайта не попадает, восстановлением не меняется. Порт `RemoteStore` (`domain/ports.ts`), адаптер — `s3Remote`
(`infrastructure/s3-store.ts`).

**Когда отправляется.** После каждой копии `backups.run` — по расписанию и кнопкой «Сделать копию сейчас» — если
хранилище включено, ключ копий есть и секрет задан. Сначала копия ложится в каталог автокопий как раньше, затем
запечатывается и уходит в хранилище под именем `<имя файла копии>.enc` (`site-auto-20261103-0330.db.enc`), затем
лишние удаляются. Отметка «копия делается» держится на всё время: вторая копия во время отправки получает
`upkeep.backup_running`. С командной строки — `cms backup --remote` (то же самое; для cron на машине без расписания).

**Хранение.** Остаются `keep` последних копий _этой_ базы: имена `<база>-auto-*.db.enc` в папке, по имени (в нём
дата). Чужие объекты, копии других баз и файлы с другими именами не трогаются (`outdatedCopies`). Отсюда правило: у
каждого сайта в общем бакете своя папка.

**Сбой — тем же путём, что сбой копии.** Не дошла копия — `upkeep.offsite_failed` в журнал сбоев и каналы
уведомлений, отметка в статусе (когда, что), `backups.run` отклоняется с этим кодом. Копия на самом сервере при этом
сделана и записана как последняя: в уведомлении так и сказано. Удачная отправка снимает отметку. Ответы хранилища —
своими кодами (`upkeep.offsite_denied`, `_no_bucket`, `_unreachable`, `_timeout`, `_not_found`), код S3 — в скобках.
У `Bun.S3Client` нет своего срока ответа, поэтому каждый запрос ограничен 120 с: зависшее хранилище иначе держало бы
отметку «копия делается» до перезапуска.

#### Запечатанный файл

Копия шифруется **на сервере, до отправки**: хранилище получает только запечатанный файл (`platform/seal.ts`).

```
 0  8  'EILESEAL'                 24 32  соль: ключ файла — HKDF(секрет, соль)
 8  1  версия формата, 1          56 16  проверка ключа (вторая часть вывода HKDF)
 9  1  содержимое: 1 — копия сайта (.db), 2 — настройки сервера (JSON)
10  1  секрет: 1 — ключ копий, 2 — пароль (PBKDF2-SHA256)
11  1  log2 размера куска: 20 — 1 МиБ
12  4  итерации PBKDF2 (у ключа — 0)
16  8  отпечаток ключа копий (у пароля — нули)
72     куски
```

- **Ключ файла свой у каждого файла**: HKDF-SHA256 от секрета (ключа копий или вывода PBKDF2 из пароля) и 32
  случайных байт соли, `info = "eile seal v1"`, 48 байт: 32 — ключ AES-256-GCM, 16 — проверка ключа в заголовке.
  Поэтому nonce можно считать от номера куска: повтора пары «ключ, nonce» нет и при сколь угодно многих файлах.
- **Куски по 1 МиБ, схема STREAM** (Hoang, Reyhanitabar, Rogaway, Vizár, 2015): nonce — 7 нулевых байт, номер куска
  (u32, BE) и байт «последний». Каждый кусок — `AES-GCM(ключ файла, nonce, кусок)` с меткой 16 байт, дополнительные
  данные — весь заголовок. Последний кусок всегда неполный (от 0 до 1 МиБ − 1), поэтому граница файла однозначна:
  `(размер − 72) mod (1 МиБ + 16)` — длина последнего куска с меткой, меньше 16 — файл повреждён.
- **Что это даёт.** Подмена байта в куске, заголовке или метке, перестановка кусков, обрезка по границе куска (у
  последнего уцелевшего нет метки «последний»), обрезка внутри куска и хвост после последнего — `seal.damaged`.
  Чужой ключ — `seal.wrong_key` с отпечатком ключа копии, до первого куска; чужой пароль — `seal.wrong_passphrase`
  по проверке ключа; копия вместо файла настроек и наоборот — `seal.other_content`.
- **Цена**: 72 байта и 16 байт на МиБ. Копия живого сайта: 44 244 992 → 44 245 752 байта. AES-GCM в WebCrypto — 64 МиБ
  за 22 мс.
- WebCrypto (`crypto.subtle`), а не `node:crypto`: AES-GCM, HKDF и PBKDF2 есть в Bun без пакетов, а куски по 1 МиБ —
  естественная граница для его однократных вызовов.

**Отправка — потоком, без файла в памяти.** Копия читается с диска по 1 МиБ, каждый кусок шифруется и пишется в
`s3file.writer({ partSize: 5 МиБ, queueSize: 2, retry: 3 })` (многочастная загрузка), `flush()` после каждого куска
держит очередь короткой. После загрузки размер объекта (`stat`) сверяется с ожидаемым. Замеры Bun 1.4.4:
- `client.write(key, Bun.file(path))` читает файл в память целиком: +84 МБ anon на файле в 66 МБ — не годится;
- `writer()` держит память ограниченной: в отдельном процессе +42 МБ anon и на 66 МБ, и на 200 МБ, от `queueSize`
  (1, 2, 4) не зависит;
- `writer.end(error)` **не отменяет** загрузку, а завершает её: объект появляется (проверено на SeaweedFS для 1 КБ и
  7 МБ). Не вызвать `end()` — объекта не будет. Поэтому `seal` зовёт `end()` только после последнего куска: сбой
  посередине (диск, шифрование) не оставит неполной копии под настоящим именем. Начатая многочастная загрузка в
  хранилище при этом может остаться: у `Bun.S3Client` нет `AbortMultipartUpload`. Совет владельцу — правило
  жизненного цикла бакета «удалять незавершённые загрузки через сутки».
- Bun подписывает запросы с `UNSIGNED-PAYLOAD`: целостность тела по дороге — забота TLS и, сверх того, меток AES-GCM.

**Восстановление.** Копия скачивается на диск (`Bun.write(путь, s3file)` пишет поток сам: +2 МБ anon) рядом с
временным файлом, распечатывается кусками в `.db` и восстанавливается как обычная копия (`app.restoreFile`: та же
проверка целостности и схемы, копия «до восстановления», пересборка контекстов).
- **В менеджере** — раздел «Копии» → «Копии в хранилище»: список, новые первыми, и «Восстановить» у каждой
  (`POST /upkeep/offsite/restore`, только после входа, как `POST /backup`). Сервер открывает своим ключом только
  копии со своим отпечатком; копия другого ключа — `upkeep.offsite_other_key` с подсказкой про командную строку.
- **С командной строки** — `cms restore --remote [<имя>|latest]`: без имени — список копий; `latest` — последняя по
  времени записи. Хранилище — из базы, если оно там настроено, поверх — флаги `--endpoint --region --bucket --prefix
  --access-key` или окружение `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `CMS_S3_PREFIX`, `S3_ACCESS_KEY_ID`. Секрет — только
  `S3_SECRET_ACCESS_KEY` или скрытый ввод: флаг остался бы в истории оболочки и в `ps`. Ключ: свой из базы, если
  отпечаток совпал; иначе ключ восстановления из `CMS_RECOVERY_KEY` или со скрытого ввода; ключ другого отпечатка —
  отказ с обоими отпечатками. База может быть новой: так сайт переезжает на чистую машину.
- Имя копии из менеджера и командной строки проверяется: только `[A-Za-z0-9._-]+\.enc`, без путей наверх.

#### Ключ копий и ключ восстановления

- **Ключ копий** — 32 случайных байта; сервер создаёт его при первом включении хранилища и хранит в `upkeep_offsite`
  (base64). Наружу его отдают только файл настроек сервера и ключ восстановления.
- **Ключ восстановления** — тот же ключ для человека: 32 байта и 2 байта контрольной суммы (SHA-256) в base32
  Крокфорда, 55 знаков группами по 5. Регистр, пробелы и дефисы не важны, O читается как 0, I и L — как 1; опечатка
  видна сразу (`seal.invalid_recovery_key`), а не после скачивания 60 МБ.
- **Показывается один раз** — в ответе, который создал ключ, как токен почтового шлюза. Менеджер показывает его
  панелью «Сохраните ключ восстановления» с кнопкой «Скопировать» и подсказкой `cms restore --remote latest`; дальше
  в статусе только отпечаток (`keyId`, 16 знаков hex). В отличие от токенов шлюза сервер ключ хранит: без него не
  запечатать следующую копию. «Один раз» — правило API, а не свойство хранения: тот, у кого есть база (root на
  сервере), ключ знает. Угроза, от которой защищает шифрование, — бакет: утёкший ключ доступа, чужой сотрудник
  хранилища, публичный по ошибке бакет. Против взлома самого сервера оно не защищает и не должно: там лежит сама база.
- **Для восстановления на новой машине нужны только** доступ к бакету и ключ восстановления.
- **Смена ключа** — «Новый ключ» (`POST /upkeep/offsite/key`): новый ключ и новый ключ восстановления, показанный
  один раз. Новые копии запечатываются новым ключом; уже лежащие в хранилище открывает только прежний ключ
  восстановления, пока хранение их не вытеснит (`keep` копий). Сервер прежних ключей не держит: связка ключей ради
  восстановления старых копий в менеджере не стоит сложности — их восстанавливает `cms restore --remote` с прежним
  ключом восстановления. Ключ меняют, если ключ восстановления потерян (сервер ещё жив — новый ключ, и сразу «Сделать
  копию сейчас») или если он мог попасть в чужие руки. Перешифровывать старые копии не нужно: их проще дождаться.
- Файл настроек сервера переносит ключ копий с собой: новая машина продолжает тот же ряд копий с тем же ключом
  восстановления. Другой ключ в файле заменяет свой, отчёт называет оба отпечатка.

### 2. Файл настроек сервера

`cms backup --server [<файл>]` пишет то, что владелец настроил на этой машине и чего нет в копии сайта, в JSON
`eile-server-settings` (версия 1), запечатанный паролем: тот же формат, секрет — PBKDF2-SHA256 с 600 000
итераций (OWASP 2023; 60 мс на машине разработки), пароль не короче 12 знаков, спрашивается дважды или берётся из
`CMS_SETTINGS_PASSPHRASE`. Без имени — `cms-server-ГГГГ-ММ-ДД.enc`, права 600. Существующий файл не
перезаписывается. Команда перечисляет, что в файле.

| В файле                                                                   | Откуда                                   |
| ------------------------------------------------------------------------- | ---------------------------------------- |
| Каналы уведомлений (SMTP, Telegram), маршруты, язык                       | `notify_settings`                        |
| Почтовый шлюз: адрес, предел, отправители, домены, **хэши** токенов       | `notify_settings.gateway`                |
| Секрет печатей форм                                                       | `forms_secret`                           |
| Расписание автокопий и проверка обновлений                                | `upkeep_settings` без итогов             |
| Хранилище копий: настройки, секрет доступа, ключ копий                    | `upkeep_offsite` без итогов              |
| Подключение ИИ с ключом                                                   | `assistant_connection`                   |
| Ключи API: хэш, подпись, последние знаки, когда выпущен — и почта хозяина | `identity_api_tokens` + `identity_users` |

Чего нет: сеансов и ссылок сброса пароля (они этой машины и этих людей), сертификатов HTTPS и учётных записей ACME
(новый сервер выпустит свои на свой адрес), очереди уведомлений, журнала сбоев и отметки работы сервера, итогов копий
и сжатий. Секреты вебхуков форм отдельно не нужны: по ADR 0037 они в настройках формы и уже приходят с копией сайта.
Секрет печатей, `forms_secret`, — другой: им подписаны печати форм, открытых до переезда.

Каждый контекст отдаёт и принимает свою часть сам — `serverSettings.{read,apply}` у `notify`, `forms`, `upkeep`,
`assistant`, `identity`; корень (`src/server-settings.ts`, `app.serverSettings`) только собирает файл и применяет его
одной транзакцией, затем пересобирает контексты. Привезённое проверяется теми же правилами, что и форма менеджера:
неверное расписание или ключ не той длины — отказ, и ничего не применено.

**Ключи API — переносятся.** Это хэши, как токены почтового шлюза, которые переносятся по условию задачи; токен из
хэша не восстановить. Файл переносит _этот_ сервер на новую машину, а не раздаёт копию в чужие руки — ради этого
ключи и не входят в копию сайта (ADR 0034). Перенос значит, что агенты и скрипты продолжают работать с новым
адресом без новых ключей. Номера пользователей на новой машине могут быть другими, поэтому ключ идёт с почтой
хозяина и достаётся пользователю с той же почтой; нет такого — ключ пропускается, отчёт называет почту. Повторное
применение ничего не удваивает (по хэшу).

**`cms restore --server <файл>`** применяет файл к базе `--db` (она должна быть: опечатка в пути не создаёт пустую
базу). Правила слияния:
- раздел, который в файле есть, заменяет свой целиком; раздела нет (`null` — на старой машине его не настраивали) —
  свой остаётся;
- итоги последней копии, отправки и сжатия остаются свои: они про эту машину;
- каталог автокопий с абсолютным путём — путь другой машины (`/home/me/backups` не существует под `ProtectHome` службы):
  он сбрасывается на `backups` рядом с базой, отчёт это называет; относительный переезжает как есть;
- ключи API — по почте, см. выше; сеансы тех, кто уже вошёл на новой машине, не трогаются.

**Путь живого сайта**: `cms backup site.db` и `cms backup --server server.enc` дома →
`sudo cms service install --domain … --from site.db` на сервере →
`sudo cms restore --server server.enc --db /var/lib/cms/site.db`. Проверено на настоящем systemd в podman
(`ubi9/ubi-init`, `--privileged`, служба с `DynamicUser`):
- под root на базе работающей службы владелец не ломается: база, `-wal` и `-shm` остаются у пользователя службы
  (uid 65012); SQLite под root отдаёт новые файлы журнала владельцу базы (ADR 0042);
- **перезапуск не нужен**: служба подхватывает настройки на ближайшем запросе — запись другого процесса меняет
  `data_version`, `app.follow()` пересобирает контексты, а с ними кэш настроек уведомлений, секрет печатей и фон
  копий с новым расписанием. API менеджера сразу показал SMTP, расписание со следующим запуском и отпечаток ключа;
  `NRestarts=0`, тот же `MainPID`. Без запросов пересборки нет: команда так и говорит и советует
  `cms service restart`, если нужно наверняка;
- затем «Сделать копию сейчас» в службе (песочница, `PrivateTmp`, `ProtectSystem=strict`) запечатала и отправила
  копию 42 МБ в хранилище за 1,7 с;
- на второй чистой машине: `cms restore --remote latest` с окружением бакета и `CMS_RECOVERY_KEY` →
  `cms service install --from` → `cms restore --server` — сайт, почта, расписание и тот же ключ копий.

### 3. Сжатие базы

`cms info` показывает свободное: «База … · 63,2 МБ · свободно 21,0 МБ (33 %) — сжать: cms compact», в JSON —
`db.free`. Менеджер — «Настройки → Копии и обновления» → «Файл базы»: размер, свободно, последнее сжатие и
«Сжать сейчас» (`POST /upkeep/compact`).

**Замеры на копии живого сайта** (63,2 МБ, 5369 свободных страниц по 4 КБ из 16 177):
- `VACUUM` — 0,45 с (три прогона: 448–454 мс), файл 63,2 → 42,2 МБ. В режиме WAL вся новая база проходит через журнал:
  он вырастает до 42 МБ, `PRAGMA wal_checkpoint(TRUNCATE)` после — 5–27 мс и обнуляет его;
- память: anon +4,8 МБ; `memory.peak` 158 МБ — это кэш страниц (чтение 63 МБ, запись журнала и временной базы), ядро
  его вытесняет;
- диск: временная база и журнал — ещё два размера живых данных (84 МБ для живого сайта);
- блокировки: сервер в другом процессе читает и пишет каждые 5 мс, пока идёт `VACUUM`. Чтения не ждали (худшее
  0,1 мс), записи ждали до 429 мс (busy_timeout 5 с), ошибок 0, чекпоинт прошёл (`busy: 0`). Внутри процесса
  сервера (bun:sqlite синхронен) на эти 0,45 с ждёт всё.

**Выбор: ночью сам и командой.** `VACUUM` на полсекунды раз в редкую ночь дешевле, чем держать файл на треть
пустым; `auto_vacuum = INCREMENTAL` потребовал бы того же `VACUUM` для перехода, страниц-указателей в файле и работы
на каждой записи ради выгоды, которая нужна раз в полгода (после переноса медиатеки, больших удалений).
- **Ночная уборка** (04:15, `tidy`, после кэша медиатеки) сжимает базу, если свободно не меньше 8 МиБ и не меньше
  пятой части файла, а на диске есть два размера живых данных (`shouldCompact`). Внутри процесса сервера: читатели
  ждут доли секунды, но ни одна запись не получит `SQLITE_BUSY` — у сервера одно соединение.
- **`cms compact`** — сжать сейчас, без порогов; можно на работающем сайте. На базе в сотни мегабайт запись сервера
  ждала бы дольше `busy_timeout` и получила бы `SQLITE_BUSY`: для таких баз — ночь или «Сжать сейчас» в менеджере, то
  есть внутри процесса сервера.
- Места на диске мало — `upkeep.no_disk_space`, база не тронута. Итог последнего сжатия (когда, до, после, сколько
  длилось) — в `upkeep_settings`.

## Замеры памяти

Копия живого сайта (`sqlite3 … .backup`), её копия сайта — 42,2 МБ. Хранилище — SeaweedFS (`chrislusf/seaweedfs`) в podman
на этой же машине: образы MinIO в quay.io и Docker Hub больше не раздаются (`unauthorized`/`denied`).
Пик RSS команд — `getrusage` (`/usr/bin/time`), по три прогона, `NODE_ENV=production`, временный каталог на диске:

| Команда                                              | Время       | Пик RSS    |
| ---------------------------------------------------- | ----------- | ---------- |
| `cms info` (запуск программы, для сравнения)         | 0,23 с      | 148 МБ     |
| `cms backup` (VACUUM INTO)                           | 0,54 с      | 150 МБ     |
| `cms backup --remote` (копия, печать, S3)            | 0,82–0,87 с | 152–153 МБ |
| `cms restore --remote latest`                        | 0,48–0,50 с | 182–183 МБ |
| `cms restore копия.db` (прежний путь, для сравнения) | 0,48 с      | 228 МБ     |

Отправка добавляет к копии 2–3 МБ пика. Восстановление из хранилища легче восстановления из файла: файл копии
прежний путь читает в память целиком, а здесь копия идёт с диска на диск кусками.

Сервер из исходников под `systemd-run --user -p MemoryMax=330M -p MemorySwapMax=0`, база на диске, вход в менеджер
и прогрев страниц, затем один запрос; по три прогона на свежем сервере. `VmHWM` процесса — 218–242 МБ уже после
запуска, и ни копия, ни отправка, ни восстановление его не подняли:

| Запрос                                         | Время       | VmRSS до → после |
| ---------------------------------------------- | ----------- | ---------------- |
| «Сделать копию сейчас», хранилище выключено    | 0,36–0,44 с | +3…+5 МБ         |
| «Сделать копию сейчас» с отправкой в хранилище | 0,67–0,75 с | +6…+11 МБ        |
| «Восстановить» копию из хранилища              | 0,40–0,42 с | +13 МБ           |

Все прогоны — `Result=success`, без OOM. Сэмплер `memory.stat` снаружи для таких коротких запросов не годится:
статистика cgroup обновляется с задержкой, пики то видны (+70 МБ — тот же `VACUUM INTO`), то нет; поэтому —
`VmHWM`/`VmRSS` процесса и `getrusage`.

## Как проверить с настоящим S3 руками

Тесты (`tests/offsite.test.ts`) гоняют настоящий `s3Remote` и `Bun.S3Client` против учебного хранилища на `Bun.serve`.
С настоящим S3-сервером — так (MinIO подойдёт так же, если найдётся образ):

```sh
podman run -d --name eile-s3 -p 127.0.0.1:8333:8333 -v $PWD/s3.json:/etc/s3.json:ro \
  docker.io/chrislusf/seaweedfs server -dir=/data -s3 -s3.port=8333 -s3.config=/etc/s3.json
curl --aws-sigv4 aws:amz:us-east-1:s3 --user "$KEY:$SECRET" -X PUT http://127.0.0.1:8333/copies   # бакет
# менеджер: «Копии вне сервера» — http://127.0.0.1:8333, бакет copies, ключ и секрет; «Проверить связь»
cms backup --remote --db site.db
S3_SECRET_ACCESS_KEY=… cms restore --remote --db site.db                       # список
S3_ENDPOINT=http://127.0.0.1:8333 S3_BUCKET=copies S3_ACCESS_KEY_ID=… S3_SECRET_ACCESS_KEY=… \
  CMS_RECOVERY_KEY=… cms restore --remote latest --db fresh.db                  # чистая машина
podman rm -f eile-s3
```

`s3.json` — `{"identities":[{"name":"eile","credentials":[{"accessKey":"…","secretKey":"…"}],"actions":["Admin","Read","List","Write"]}]}`.
Так проверены: проверка связи (и `NoSuchBucket` до создания бакета), отправка 42 МБ, список, восстановление в ту же
базу ключом сервера и на новую базу ключом восстановления, служба в песочнице (см. выше).

## Что не проверено

- Настоящие DigitalOcean Spaces, Backblaze B2, Hetzner и AWS: проверены учебное хранилище тестов (`tests/fixtures/s3.ts`,
  то подмножество API, которым пользуется `Bun.S3Client`) и SeaweedFS. Virtual-hosted style (`bucket.host`) не
  проверен ни на одном.
- Что делает Bun с многочастной загрузкой при обрыве сети посередине: отменяет ли её. На случай, если нет, —
  правило жизненного цикла бакета.
- Срок 120 с на запрос не проверен на настоящем зависшем хранилище.
- Ночное сжатие проверено правилами и вызовом, а не ночью в `Bun.cron` под нагрузкой.

## Последствия

- Копии переживают смерть сервера и аккаунта; для восстановления нужны доступ к бакету и ключ восстановления. Потерять
  ключ восстановления, пока сервер жив, не страшно: новый ключ и новая копия. Потерять его вместе с сервером — копии в
  хранилище не откроет никто.
- В бакете видны имена копий (имя базы и время) и их размеры. Подменить копию другой настоящей копией того же ключа
  (откат) тот, у кого есть запись в бакет, может: имя объекта в запечатанный файл не входит. Ключ доступа стоит
  выпускать на один бакет; удаление старых копий требует права удалять.
- Переезд на новый сервер — четыре команды и ни одного поля в менеджере: копия, файл настроек, `service install
  --from`, `restore --server`. Файл настроек — как пароль: в нём пароль почты, ключ ИИ и ключ копий.
- Файл базы больше не растёт навсегда: ночью он сжимается сам, `cms info` и менеджер показывают, сколько в нём пусто.
- API: `app.restoreFile`, `app.serverSettings.{read,apply}`; `upkeep.offsite.{status,configure,rotate,check,store,copies,fetch,key}`,
  `upkeep.database.{status,compact,tidy}`, `upkeep.serverSettings`; `serverSettings` у `notify`, `forms`, `assistant`,
  `identity`; в `platform` — `seal.ts`, `databaseSpace`, `compactDatabase`. Маршруты менеджера: `PUT /upkeep/offsite`,
  `POST /upkeep/offsite/check`, `POST /upkeep/offsite/key`, `GET /upkeep/offsite/copies`, `POST /upkeep/offsite/restore`,
  `POST /upkeep/compact`; секрет, ключ и восстановление — только после входа, не ключом API.
- CLI: `cms backup --remote`, `cms backup --server`, `cms restore --remote`, `cms restore --server`, `cms compact`; флаги
  `--endpoint`, `--region`, `--bucket`, `--prefix`, `--access-key`; окружение `S3_*`, `CMS_S3_PREFIX`,
  `CMS_RECOVERY_KEY`, `CMS_SETTINGS_PASSPHRASE`.
