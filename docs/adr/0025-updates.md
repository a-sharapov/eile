# 0025. Проверка обновлений и `cms update`

- Статус: принято
- Дата: 2026-10-31

## Контекст

Программа ставится установщиком из релизов GitHub (ADR 0023). Обновиться можно повторным запуском установщика, но
о новой версии владелец сайта не узнаёт: менеджер молчит, а в релизы никто не заглядывает.

## Решение

**Сервер раз в сутки спрашивает страницу релизов** (`GET /repos/<owner>/<name>/releases` у API GitHub).

- **Когда:**
  - первая проверка — через 30 секунд после запуска;
  - дальше раз в сутки в случайную минуту, чтобы серверы не стучались все разом.
- **Что уходит:** адрес списка выпусков и `User-Agent: Eile/<версия>` (без него GitHub отвечает 403). Ни адреса
  сайта, ни чего-то о нём.
- **Хранение:** результат лежит в памяти. В `/session` он виден только тем, у кого есть право `site.edit`. В меню
  профиля появляется «Доступна версия X» со ссылкой на выпуск, а на аватаре — точка акцентом.
- **Как выключить:**
  - флажок «Проверять обновления» в «Настройках → Копии и обновления»;
  - на сервере — переменная `CMS_NO_UPDATE_CHECK=1`, тогда флажок в менеджере заблокирован.

**Какая версия считается новее** — по semver, включая метки пре-релизов: `1.0.0-alpha < 1.0.0-alpha.1 <
1.0.0-beta < 1.0.0-rc.1 < 1.0.0`.

- Пре-релиз идёт в счёт, только если и установлена пре-релизная версия: с альфы зовём на следующую альфу, со
  стабильной — только на стабильную.
- Признак пре-релиза берётся из самой версии, а не из флажка GitHub: альфа может быть помечена Latest (ADR 0023).
- Черновики и неразборчивые теги пропускаются.

**`cms update [--check]`** повторяет установщик, но без shell:

1. Сборка под эту систему выбирается так же, как у `install.sh`: `linux-x64`, `linux-arm64-musl`,
   `darwin-arm64`. musl определяется по `/etc/alpine-release` и `ldd --version`, x64 под Rosetta берёт родной
   arm64.
2. Скачиваются `cms-<цель>.gz` и `SHA256SUMS`. Сумма сверяется до распаковки.
3. Новый файл пишется рядом со старым: `.cms.new.<pid>`, права 755.
4. Пробный запуск `version`: не запустился — файл удаляется, установленный `cms` не тронут.
5. Прежний бинарник сохраняется как `cms.old`, новый переименованием встаёт на его место.

Работающий сервер доживает на старом файле, поэтому команда просит перезапустить его. Запущенное из исходников
(`bun src/main.ts`) не обновляется: `Bun.isStandaloneExecutable` ложно, и это говорится прямо.

## Последствия

- Обновление — одна команда, и откатиться просто: вернуть `cms.old`.
- Сервер без выхода в интернет проверку не пройдёт. Сбой только пишется в журнал, менеджер ничего не показывает.
- Без токена API GitHub даёт 60 запросов в час на адрес. Одной проверки в сутки хватает с большим запасом.

## Дополнение: своя лента (0.1.0-alpha.9, 2026-11-03)

`CMS_RELEASES_URL` заменяет `https://api.github.com` и в `cms update`, и в проверке сервера: зеркало, сеть без
выхода наружу, проба обновления и отката без пересборки. Только https; http — на этой машине или с
`CMS_RELEASES_INSECURE=1`, и те же правила — для файлов выпуска ([ADR 0048](0048-health-releases-url-redirect-check.md)).

## Дополнение: потоком через диск (0.1.2, 2026-11-05)

До 0.1.2 `cms update` держал в памяти архив дважды (`response.bytes()` и копию для `Bun.gunzipSync`) и
распакованный бинарник: около 250 МБ при архиве 58 МБ. На сервере с 445 МБ памяти рядом с работающим сайтом
его убивал OOM; сайт при этом работал дальше на старом файле.

Теперь в памяти только куски потока:

1. Сначала скачивается `SHA256SUMS`. Строки архива в нём нет — отказ до загрузки архива.
2. Рядом с бинарником создаётся пустой `.cms.download.<pid>`. Писать в каталог нельзя — `upkeep.no_write`
   тоже до загрузки.
3. Архив идёт потоком в этот файл, SHA-256 считается по дороге. Не совпала — файл удаляется нераспакованным.
4. `.gz` распаковывается потоком (`DecompressionStream`) в `.cms.new.<pid>`. `.zip` для Windows читается
   целиком: каталог файлов у zip в конце, а памяти у машин с Windows обычно хватает.
5. Дальше как раньше: пробный запуск, `cms.old`, переименование. Временный архив удаляется при любом исходе.

Замер на сборке 0.1.2 со своей лентой (`CMS_RELEASES_URL`) и архивом 61 МБ: пиковый RSS 91 МБ против 404 МБ у
0.1.1, вместе со страницами самого бинарника. Под `systemd-run -p MemoryMax=160M -p MemorySwapMax=0` 0.1.1 убит,
0.1.2 обновляется и при 64 МБ. Тест в `tests/upkeep.test.ts` отдаёт выпуск в 64 МБ кусками по запросу и перед
последним куском смотрит, сколько уже в `.cms.download.<pid>`: у потока — 93 %, у прежнего кода — ничего. Память
процесса тест не меряет: на раннере GitHub без нехватки памяти сборщик мусора не спешит, и рост там 117–212 МБ
против 60–80 у разработчика, а предел cgroup выше показывает настоящую картину.

`install.sh` по той же причине скачивает и распаковывает во временный каталог внутри каталога установки, а не
в `/tmp`: на Fedora и во многих других системах это tmpfs, то есть та же память, а архив с бинарником — под
200 МБ. Новый файл встаёт на место одним переименованием, права на каталог проверяются до загрузки.
`install.ps1` пробует загрузку трижды и при отказе называет причину, а не только «download failed».
